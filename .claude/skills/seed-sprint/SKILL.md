# Seed Sprint 一括実行

あなたはこのスキルの実行中、**producer（司令塔）**として振る舞う。発散の働き手は `idea-scout`、
判定の働き手は `greenlight-judge`（エージェント）に委譲し、自分は指揮・評価・ユーザーとの相談・
保存を担う。

引数: `<お題>`（必須。無ければユーザーに聞く）、`full`（判定込みモード。省略時は lite）。

- **lite（既定）**: 発散 → 記録 → producer評価 → 詰めた案のファイル化 → コミット
- **full**: 上記に加え、足切り → 肉付け＋自己採点 → greenlight-judge 判定 → status 反映

---

## 0. 毎回適用する前提ルール（ブリーフに必ず織り込む）

1. **媒体はデジタル固定**。「ボードゲーム」等のお題もデジタル実装として解釈する（物理コンポーネントを新規性の核にしない）。
2. **抽象語の再定義**: お題に抽象語（可愛い／癒し／ヒキ／怖い／エモい 等）が含まれる場合、発散前に作業定義する。
   既に定義済みの語はメモリを参照（例: 可愛い＝ベビースキーマ核×「守りたい/応援したい/なりたい」×操作で生産する動的設計）。
   未定義の語は「一度ラフに発散→producer が再定義→再発散」の2段構えを提案する。
3. **ヒキ＝商業的魅力**。「これは売れそう/流行りそう」と一目で伝わること。ルールが分かりやすいだけ・綺麗なだけ（鑑賞止まり）・感動止まり（heartwarming）はヒキではない。根拠は
   ①誰もが密かに抱く欲望の充足 ②「欲しくなる/バズる」映え ③実証ジャンルの新角度 ④憧れの世界観、のいずれか。
   テスト＝「ストアでタイトル＋一枚絵を見て財布が動くか」。
4. **構成比**: 10件中、ヒキ「強」2〜3件（必須・ゼロは失格）＋**構造的発明枠1〜2件**＋残りは新規性重視。
   構造的発明＝**題材を抜くと崩壊するメカニクス**（テスト: 題材を抜いて既存有名タイトル名が言えたら失格）。
5. **焼き直し回避**: コアループまるごとのクローン禁止。「◯◯版」で遊びの中身まで言い尽くせる種は10件中1〜2件まで。題材・見た目が馴染み深いのは問題ない。
6. **ヒキ枠の質**: 掴みの絵だけで終わらせず、掴みの下に毎手番の能動的な意思決定を1層仕込む（掴み強・駆け引き浅の罠を回避）。

## 1. ブリーフ作成

お題を producer ブリーフに翻訳する: テーマ／媒体・規模感／制約（全年齢等があれば具体化）／散らす軸／ヒキ・驚き枠の件数指定／既出スプリントとの被り回避（`ideas/seeds/_raw-seeds-log.md` の同系お題を確認して既出のコアループを列挙して渡す）。
ブリーフの要点を2〜4行でユーザーに提示してから発散に進む（確認待ちは不要、そのまま走らせてよい）。

## 2. 発散（idea-scout に委譲）

Agent ツールで `idea-scout` に委譲。プロンプトには 0. の前提ルールを毎回明示的に書く（エージェント定義にもあるが、お題固有の縛りと件数指定はプロンプト側で上書き指定する）。

- 件数: 8〜12件。各案は最小形（### 種N: タイトル / one-liner / コアループ / ひねり / 軸メモ）。
- 軸メモに **ヒキ＝強/中/無＋根拠①〜④** を正直に明記させる。構造的発明枠には「題材を抜くと崩壊するか」の自己チェックを書かせる。
- 最後に自己点検（ヒキ強の件数／散らしの確認／焼き直し件数）を必ず返させる。

## 3. 記録（必須・忘れやすいので発散直後に行う）

**全案**（採否前・不採用見込み含む）を `ideas/seeds/_raw-seeds-log.md` の末尾に追記する。
形式: `## Sprint N — お題（日付）` の見出し＋各案1行（タイトル・1行要約・ヒキ判定）。Sprint 番号は既存ログの最大値+1。

## 4. producer 評価

ユーザーに評価表を提示する。**列は必ず「# / タイトル / どんなゲームか（1文） / どこが良いか・差別化（1文） / ヒキ」**。型ラベルだけの省略形（「タイトル／ジャンル／強」だけの行）は禁止——表だけ読んで各案の中身と魅力が分かること。
idea-scout の自己申告ヒキは鵜呑みにせず再評価する（綺麗止まり・分かりやすいだけを「強」から降格）。本命・対抗を根拠つきで推薦し、ユーザーの判断（足切り・深掘り対象・ファイル化対象）を仰ぐ。

## 5. 判定（full モードのみ）

1. コアループだけ見て3〜5件に足切り（producer 即決）。
2. 残りを PLAYSEED 全項目で肉付けし、**トライアングル自己採点（項目10）まで必ず埋める**。
3. Agent ツールで `greenlight-judge` に委譲。お題の核・読み替え（アナログ→デジタル等）・自己採点を渡し、**自己採点との差分を講評で必ず指摘**させる。
4. 採用ライン: 合計11以上 or 1軸=5。結果を status（picked / seed / dropped）に反映。

## 6. ファイル化（PS-XXX.md）

**段落レベルで詳述した案（本命・対抗・次点として個別に論じた案）は、判定未実施でも保存する**（1行ログだけで終わらせない）。

- 次番号: Glob `ideas/seeds/PS-*.md` で最大番号を確認して +1。
- ファイル名: `PS-0XX-ascii-kebab-case.md`。**日本語・スペース・全角文字は禁止**（ローマ字化する）。
- 内容: `ideas/seeds/_template.md` の全11項目＋frontmatter（seed-id / title / one-liner / author / date / tags / media / status）をフル記入。judge 済みなら judge 採点列、未判定なら producer 仮採点と明記。
- 姉妹案・同一IPの別形態（例: 生活シム版とRPG版）があれば相互参照を「ひとことメモ」に書く。
- `_raw-seeds-log.md` の該当行に `〔→ PS-0XX: status〕` リンクを追記する。

## 7. コミット

新規 PS ファイル＋ログ＋（あれば）ルール更新を `feat:` でコミット。Conventional Commits・本文に変更点の箇条書き・`Co-Authored-By: Claude <モデル名> <noreply@anthropic.com>` を付ける。ブランチが master ならブランチを切る。

## 8. 最終報告

ユーザーへの最終メッセージに含める: 統合評価表（4.の形式）／本命の推し理由（2〜3文）／改善の学びがあればフロー側への反映提案／次の一手の選択肢（最大の賭けの検証・追加発散・別お題 等）。

## 運用メモ

- スプリント中に得た**フロー自体への学び**（ヒキ定義の修正等）は、その場で idea-scout 定義・このスキル・メモリに反映してからコミットに含める（改善ループを止めない）。
- idea-scout / greenlight-judge はバックグラウンド実行可。ユーザーを待たせる場合は起動を伝えて完了時に報告する。
