# ADR-0008: Dragon Tideの販売用パッケージと継続更新

- 日付: 2026-11-03
- 状態: 採用
- 対象: Steam / Windows、Android、iOS
- 起点: GitHub masterのDragon Tide v3.68.0

## 背景

Dragon TideはスマホとPCでユーザーによるテストプレイが継続されている。今回の目的は、ゲーム内容を再評価することではなく、全プラットフォームで買い切り販売し、その後も頻繁に更新できる配布基盤を作ることである。

ゲーム本体は `prototypes/dragon-tide/index.html` とそのアセットにある。OSごとにゲームを複製して修正すると更新漏れが起きるため、本体は一か所で管理し、配布時に各プラットフォーム用の形式へ包装する。

## 決定

### 1. 共通ソースと包装を分ける

- `prototypes/dragon-tide/` をゲームの共通ソースとする。
- `release/dragon-tide/` を配布設定、生成処理、ラッパーのルートとする。
- Windows版は **Electron 45.2.1**、Android/iOS版は **Capacitor 8.6.0** を採用する。
- バージョンを固定し、依存関係の更新はゲームの変更と区別してレビューする。
- ローカルのゲームとアセットをアプリへ同梱する。起動時に配信用Webサイトを読み込む方式にはしない。
- 今回はゲーム本体の全面的な分割、エンジン移行、ゲームバランスの再検証を要求しない。

### 2. ストアの更新経路を使う

全プラットフォームを買い切りとする。広告、消耗型課金、製品版解放課金を配布基盤の前提にしない。

Windows / SteamはSteamPipe、AndroidはGoogle Play、iOSはApp Storeの配布・更新機構を使う。独自OTA、独自更新サーバー、Electronの別経路の自動更新は追加しない。CIは成果物を作成し、ストアへの実公開は手動とする。

### 3. 表示バージョンと配布番号を分ける

- ゲーム内 `GAME_VERSION` を表示バージョンの唯一の情報源とする。
- リリース設定の `buildNumber` を配布ごとに単調増加させる。
- リリースタグは `dragon-tide-vX.Y.Z-build.N` とする。`X.Y.Z` は `GAME_VERSION`、`N` は `buildNumber` と一致させる。
- 同じゲームバージョンで包装や署名を修正して再提出する場合も、配布番号を増やして識別する。
- 成果物をコミットとタグへ結び付け、どのゲームを提出したか追跡できるようにする。

### 4. アプリの識別子と保存先を固定する

暫定アプリIDは `com.shuuterweb.dragontide`。正式配布前に開発者が所有する識別子として確定し、`identityConfirmed` を設定する。未確定の識別子で本番配布を進めない。

公開後はアプリID、WebViewのorigin、アプリのユーザーデータ保存先を変更しない。変更が必要な場合は先に保存データの移行方法を設計する。OS別のアプリ内保存領域は独立しており、ブラウザで遊んだデータや別プラットフォームのデータが自動で引き継がれるとは扱わない。

### 5. セーブ互換性を更新の確認項目にする

現行のプロフィールはv1、ラン保存はv2。ゲームの表示バージョンを上げるだけで保存形式の番号を上げない。保存構造や意味が変わる場合に、読み込み側の移行と併せて変更する。

ラン保存には生成地形に対応するbitsetが含まれるため、**保存スキーマ番号が同じでも、地形生成や建物の順序・件数の変更によって意味が変わり得る**。更新時に既存ランを継続できるかを判断し、必要なら旧生成方式の保持、変換、またはプロフィールを維持した明示的なラン再開始を設計する。互換性がないデータを黙って新地形へ適用しない。

セーブ保持と起動・同梱アセット等の配布確認は行うが、ゲームの面白さや全内容の再テストをリリース基盤のゲートにしない。

### 6. CIと秘密情報を分ける

CIではソース検査、パッケージ生成、成果物保存を行う。未署名の成果物と、署名情報を設定した場合の署名ビルドを区別する。ストアのアカウント、アプリID、証明書等が未登録でも基盤の整備を進められる構成とする。

証明書、秘密鍵、キーストア、パスワード、ストアの認証情報はGitへ保存しない。ストアへの提出成功や審査通過を、未署名ビルドの成功だけで報告しない。

## 結果

日常のゲーム更新は共通ソースへ反映し、表示バージョンと配布番号を更新して同じコマンド・CIから各プラットフォームの成果物を作る。ストア側の提出・承認・公開は別の段階として管理する。

Electron / Capacitor自体の更新、署名環境、各ストアの要件には継続保守が必要になる。具体的な運用手順は [Dragon Tideリリース運用](../releases/dragon-tide.md) に記載する。
