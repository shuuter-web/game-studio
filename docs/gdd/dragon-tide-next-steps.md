### 2-1b. ステージ側の攻略要素（v0.41 で着手）

**ボス周辺の密度**（実機判定 2026-08-18「ボス周辺はもっと建物や敵を密集させたい。
建物密度は大きめの街と同等以上に」）に対応済み。次は §3-1 の攻略対象そのものの拡張へ。

| 変更 | 内容 |
|---|---|
| 城下の充填方式 | ランダム試行 → **同心リング上の候補列（六方最密相当）をシャッフルして詰める**。旧方式は密度を上げようとしても後半が全部弾かれ、棟数を増やしても密にならなかった |
| 充填範囲 | リング外側(188px)から → **ボス至近(68px)から城壁内側(400px)まで** |
| 間隔 | 32px → **22px**（街の small 同士は24px。首都は一段詰める） |
| 構成 | large リング＋small → **large リング＋medium(外周のみ)＋small**（街と同じサイズ構成にして「市街」に見せる） |
| 守備隊 | **新設**。`BOSS_GARRISON_BY_STAGE` で城壁の内側(200〜395px)だけを巡回する敵を配置。従来 `generateMovers` はボス圏内を明示的に避けており**ボス周辺に敵が1体も居なかった** |
| 民家の射撃 | **街と同じだけ撃つ**（`CAPITAL_SMALL_SHOOTER_RATE = 1.0`）。v0.41 では 0.06 まで絞ったが、**その結果ボス周辺が普通の街より弱くなった**（実機判定 2026-08-21「弱くする必要はない」）→ v0.43.1 で全戸射撃に戻した |

**踏んだ罠と、その後の揺り戻し（記録）**：密度を5倍にしたら**建物の射撃も5倍**になり、
群れ35体が2秒で全滅した（同一レイアウトA/Bで切り分け。原因は建物の射撃で、守備隊でも衝突でもない）。
そこで射手を6%まで絞ったが、**今度はボス周辺が普通の街より弱くなった**＝行き過ぎだった。
v0.43.1 で全戸射撃に戻し、射手の数はボス周辺147〜174／最も濃い街122〜180（比0.84〜1.22）＝**街と同等**。
そこへ要塞リングのカタパルト16基・城壁・守備隊・ボス本体が上乗せされるので**総合では街より明確に強い**。
教訓は「密度と弾量は連動する」であって「弾を減らせ」ではない。減らすのは
「城下は無防備な民家」という別の設計を選ぶときだけにする。

**v0.43.1 の実測（ボス突入シナリオ）**：
STAGE4・実プレイ相当（100体＋強化カード）＝**6.6秒でボス撃破**・329棟破壊・群れ90〜100体を維持。
STAGE8・同条件＝**44秒で撃破**・251棟破壊（12秒あたりで一度0体まで落ちてから90体へ復帰＝波状の攻城戦になる）。
STAGE4・強化なし60体＝29.4秒で撃破・146棟破壊（生存3〜33体で綱渡り）。

**実測（STAGE8・同一レイアウト・群れ60体固定）**：
現状は STAGE1/4 でボス撃破（群れ57/40体生存）。STAGE8 は強化なしの60体では落とせないが、
これは v0.40 相当（城下を撤去した状態）でも同じ＝**この変更が原因ではない**。
実プレイ相当（100体＋強化カード数枚）なら **40秒でボス撃破・291棟破壊・守備隊21体中19体撃破・群れ100体生存**。

### 2-1c. 攻略対象の拡張（v0.42 で着手）

実機判定（2026-08-20）で**採否がはっきり決まった**。以降この判断に従う。

| 案 | 判断 | 理由 |
|---|---|---|
| 収穫者（卵/XPを奪って逃げる） | **不採用** | 画面にXPがあまり残らない／**卵を取られるのは強い不快感**。「急ぐ理由」は別の手段で作る |
| 誘爆（火薬庫の連鎖爆発） | **敵側では不採用** | やるなら**竜側のスキル**として。敵の持ち物としては不要 |
| 鏡の盾兵 | **採用** | 実装済み |
| 分裂体 | **採用** | 実装済み |
| 潜行者 | **採用**（定番だが良い） | 実装済み |
| 持続する範囲攻撃 | **採用**（複数バリエーション。**建物側にも**） | 実装済み（敵2種＋建物1種） |

実装したもの：

| 要素 | 挙動 | 操作がどう変わるか |
|---|---|---|
| 🛡 **鏡の盾兵**（`shieldman`・4体1隊） | 進行方向±66度からの被弾を**完全に弾く**。追跡型なので盾は常に群れを向く | **回り込む**。横・背後からは通る（実測: 正面0／背後10／真横10ダメージ） |
| 🫧 **分裂体**（`splitter`） | 壊すと2体、その子もまた2体（1→2→4） | 早めに潰しきるか、無視して本命へ行くかの判断 |
| 🕳 **潜行者**（`lurker`） | 潜航中は**無敵・攻撃なし**（3.4秒）／浮上中だけ殴れる（2.6秒） | 浮上の瞬間に群れを乗せるタイミング合わせ。浮上直前は輪が強く脈打つ |
| 🔥 **火吹き車**（`flamewagon`） | **群れの足元**に燃える帯（半径110・3.6秒・5.5dps） | その場から退く。留まると効く |
| ☁ **瘴気塔**（`miasma`・静止） | 自分の周りに**広がる雲**（60→230・5秒・3.0dps） | 近寄れない領域ができる |
| 🗼 **焼夷塔**（建物・ステージごとに1〜8基） | large 建物の一部が周期的に燃える輪（半径145・4秒・4.0dps）を張る | 街の中に踏み込むと足元が燃える＝**建物側にも退かせる圧** |

**危険地帯（hazard）の共通仕様**：`spawnHazard(x,y,radius,life,dps,color,growFrom)` で誰でも置ける。
**必ず 0.7秒の予告**（輪が点滅・無害）が先に出る＝理不尽に見えない。ダメージは0.25秒刻み。
ステージ切替とクリア演出で消える。実測: 予告中0ダメージ→20体×6dps×1.5秒で**ちょうど180**。

**難度への影響（同一レイアウト・群れ60体固定のA/B）**：
STAGE1 は差なし（潜行者1体のみ）。STAGE4 は生存62→39だが**ボス撃破は維持**。
STAGE8 は生存28→0（ただし v0.42 以前でもボスHP85%残しで失敗しており、
強化なし60体では元から届かない）。**実プレイ相当（100体＋強化カード数枚）では
STAGE8 のボスを29.6秒で撃破・297棟破壊・群れは98体まで回復**。

**測定時の罠（記録）**：同一レイアウトA/Bで**前の試行がボスを倒すと `gameState` が
stage-clear に落ち、次の試行では竜の攻撃が全部止まる**（破壊数0の異常値になる）。
毎フレーム `gameState = "playing"` を強制してから測る。

### 2-1d. ダム／堰と雷撃塔車（v0.43）

next-steps §3-1 の残り推し順のうち上位2つを実装した。

| 要素 | 挙動 | 実測 |
|---|---|---|
| 🌊 **ダム／堰**（各ステージ1基・川の中流） | HPは large の6倍（約560）。**壊すと下流へ水の壁が走り、通った帯の建物が順に崩れる**（速度900px/s・帯の幅460px）。城壁とボスは流されない | 決壊から**2.3秒で419棟が水没**。「1つ壊すと広域が落ちる」＝俯瞰で最も映える枠 |
| ⚡ **雷撃塔車**（`teslawagon`） | 最寄りの竜に落ちてから**触れ合っている仲間へ幅優先で広がる**。1体ごとのダメージは**その竜の周りの密度に比例**（最大3.2倍） | 30px間隔で密集＝16体感電・1体あたり9.7／40px一列＝16体・5.6／95px散開＝**1体・3.4**。固めるほど痛い |

**雷撃塔車で作り直した点（記録）**：当初は「連鎖の長さ」で密集を罰する設計にしたが、
**Boids の群れは線に伸ばしても分離半径28前後で並ぶので、どう動かしても最大まで連鎖した**
（実測: 広がり300pxでも6連鎖）。連鎖の長さではなく**1体ごとの密度倍率**に変えて成立させた。
さらに2つ潰した：①落雷点が群れの端のはぐれ個体だとそこで途切れる（→隣を持つ竜を選ぶ）
②上限に達すると残りが無傷のまま終わる（→集める処理とダメージを配る処理を分ける）。

### 2-1e. 敵を確認するデバッグ機能（v0.44）

マップが 4800×3600 あるので、**特定の敵の挙動を見たいときに「探す」のが最大の手間**だった。
「呼ぶ・見分ける・落ち着いて眺める」の3つを用意した（デバッグパネル内。既定はすべてOFF）。

| 機能 | 内容 |
|---|---|
| 👾 敵を出す… | 図鑑（18種）から選ぶと**群れの300px隣に湧く**。隊で出る敵は隊ごと（盾兵×4・騎士団×8・マンモス×3）、巨獣はコア＋腕2本まとめて |

#### 踏んだ罠（記録）

1. **`MAX_ATTACK_RADIUS = 380` が実効射程の上限だった**。建物の攻撃判定は
   「竜の位置から `_ATKCELL_RADIUS` セル内の建物を集める」逆引き方式なので、
   `attackRadius` をいくら広げても **400px より遠い群れは集合に入らず永久に撃たない**。
   プリズム塔（射程620）が496px の群れに10秒間0ダメージで発覚した。
   **v0.48 のロケット砲台（射程465と称していた）も実効400px だった**。
   → 走査半径を「置かれた建物の最大 attackRadius」から毎ステージ計算する
   （`recomputeAttackQueryRadius`、`cacheBossIndex` から呼ぶ）。射程は 520 までに揃えた
   （クエリ費用は半径の2乗で効くため）。
2. **首都の一斉射が届かなかった**。`spawnFanProjectileRaw` の catapult 弾は
   `PROJECTILE_MAX_RANGE=420` で消えるので、600px 先の群れに1発も届かない（実測0ダメージ）。
   → 個別の飛距離上限 `projRange` を追加した（0 なら kind ごとの既定値）。
3. **囲むだけの円は当たらない**。神託の光柱を半径168の円周に立てたら中心が安全地帯になり、
   居座った群れに**0ダメージ**だった。内側(62)と外側(140)を交互にして重心を覆う形に変えた。
4. **散らす技は測るたびに数字が暴れる**。矢の雨 27〜75、対空弾幕 18〜165。
   発数を増やして範囲を締めると安定する（34発/175px・26発/150px）。
5. **動員段階が上がると射程が消えた**。`reinforceSettlementForTier` が
   `attackRadius` を街の既定値に戻すため、段階1に上げた瞬間に投石機が 500→400 に縮んでいた
   （v0.48 の焼夷塔・ロケット砲台も同じ穴に落ちていた）。→ 補強のあとに兵器の射程を貼り直す。
6. 測定の作法: `applyDamageToBoid` を差し替えてダメージを積算し、**竜を毎フレーム同じ位置に置き直す**
   （`simStep` を呼ばない）。動かすと避けてしまい、技が機能しているのか当たっていないだけなのか分からない。

### 2-1h. 首都の増援と城壁の厚さ（v0.58）

実機判定（2026-09-02）「ボス戦で取り巻きを倒してしまうと後は消化試合になる。
動く敵が増援として出てくるようにできないか。全体的に壁はもっと硬くていい」。

#### 首都の増援（`updateBossReinforcements`）

守備隊は**置いてあるだけの有限な数**なので、片付けたあとの首都は
「建物の弾を浴びながらHPを削るだけ」になっていた。首都が兵を出し続けるようにした。

| 決め事 | 値 | 理由 |
|---|---|---|
| 発動条件 | 群れ重心が首都から720px以内 | 離れれば止まり、タイマーも巻き戻る＝逃げれば追撃されない |
| 出現位置 | 首都中心から150px・群れの方向へ±0.6rad | **城から出てくる**のが見えるので理不尽にならない |
| 顔ぶれ | `BOSS_GARRISON_BY_STAGE[era]`（数の重みで抽選） | 時代の手触りを崩さない |
| 3波ごと | その文明の看板ユニットが先鋒 | 波が進むほど重くなる |
| 頭数 | 第1波4体→波ごとに+1（上限12） | |
| 間隔 | 13秒。**前の波を全滅させたら4秒**まで詰める | 固定間隔だと「湧く→即殲滅→10秒の空白」で消化試合が戻る（実測） |
| 同時生存 | 22体まで | 溜めて処理落ちさせない・囲まれ殺しにしない |

実測（35体を首都の300px手前に固定・60秒・竜は無敵）:

| 文明 | 波 | 発生時刻 | 同時最大 | 敵が1体も居ない秒数 |
|---|---|---|---|---|
| I 石器 | 6波 | 9,16,25,38,45,52 | 11体 | 60秒中29秒 |
| VIII 最終 | 4波 | 9,22,35,48 | 14体 | 60秒中14秒 |

石器が空きやすいのは守備隊表が軽い（騎士・長牙のマンモス）ため。最終は
殲滅砲兵・コロッサス・治癒塔など7種が混ざって切れ目が少ない。

**掃除**: 増援は無限に湧くので、波が出るたびに死骸を `movers` から間引く
（`movers.filter(m => m.alive || !m._bossReinforce)`）。放っておくと配列が延々伸びて
毎フレームの走査が重くなる。レイダーだけが同じ掃除を持っていた。

#### 城壁（`WALL_STAGE_CONFIG`）

**HPを6倍**にした。旧値では40体の群れが1セグメントを **0.27〜0.97秒**で割っていて、
「門を探すか壁を壊すか」の判断が一切生まれていなかった。町壁は自動で0.7倍が乗る。

| 文明 | 旧HP | 新HP | 突破時間（35体を固定して焼いた実測） |
|---|---|---|---|
| III 中世 | 46 | 280 | 0.27秒 → **2.2秒** |
| VI 電気 | 72 | 440 | 0.52秒 → **8.5秒** |
| VIII 最終 | 96 | 580 | 0.97秒 → **6.3秒** |

（電気が最終より長いのは二重リングで隣のセグメントにブレスが分散するため。
硬すぎ／柔らかすぎの調整はこの表の1か所だけで効く。）

#### 負荷の実測

最終文明の首都に40体で90秒張り付いた最悪ケースで、更新処理 **7.0〜7.4ms/frame**

7msの主因は増援ではなく**最終文明のもともとの敵密度**（波が出る前から128体）。

### 2-1i. ノックバックを「攻撃を止める」意味に変える（v0.59）

実機判定（2026-09-02）「どの時代の敵もノックバック攻撃の手段を増やして。普通の街にも少数
居るくらい。ノックバック中は攻撃が止まるように。ノックバック攻撃をしてくる敵は見た目でわかるように」。

#### (1) ノックバック硬直（`boidKnockStun`）

押されている間はその竜が**一切攻撃しない**（移動は止めない）。
これで押し返しが見た目の演出から**火力の損失**になり、押してくる敵が
「先に処理する理由のある的」になる。

- 硬直 = `0.15秒 + 押し距離 × 0.0055`（上限0.85秒）
- **押し距離12px未満では硬直しない**。通常の矢は押し10pxなので素通し、
  large建物のカタパルト弾は36.7pxなので止まる＝「重い弾は手が止まる」
- **自分の攻撃の反動では止まらない**。`applyKick(..., stun=false)` を反動の2か所に渡す
  （氷槍 recoilDist=28 で実測: 押し速度25.4px/s が出ていて硬直フレームは**0**）
- 止める対象は遠隔9種＋体当たり（`updateBeamAttacks` 〜 `updateCollisionAttacks` の10か所）

#### (2) 文明ごとの押してくる敵（各1種・普通の街をまわる）

`MOVER_SPAWNS_BY_STAGE` の2番目の枠に count 2 で入れてある＝大陸全体で7体前後。
ボス周りの特殊枠ではなく**普通の街を巡回する**。守備隊表にも1体ずつ入れた。

押し方は2系統:
- **衝撃波型**（radius/push）… 面で飛ばされる。答えは「離れる」
- **射撃型**（`fan` + `kind:1` + `knockR`）… 線で飛ばされる。答えは「横へ抜ける」

| 文明 | 敵 | 型 | 押し | 実測: 攻撃できていた竜の割合の低下 |
|---|---|---|---|---|
| I 石器 | 石打ちの衆×3 | 衝撃波 r95 | 55 | 31%（70px） |
| II 古代 | 牡牛戦車 | 衝撃波 r110 | 70 | 22%（70px） |
| III 中世 | 破城槌 | 衝撃波 r125 | 85 | 26%（70px） |
| IV 近世 | 散弾砲車 | 射撃 7発 knockR46 | 弾 | 26%（70px）／**21%（250px）** |
| V 産業 | 蒸気打鉄 | 衝撃波 r130 | 95 | 45%（70px） |
| VI 電気 | 反発塔車 | 衝撃波 r150 | 115 | 59%（70px） |
| VII 大戦 | 衝撃砲 | 射撃 4発 knockR60 | 弾 | 38%（70px）／**32%（330px）** |
| VIII 最終 | 重力砲 | 衝撃波 r175 | 130 | 65%（70px） |

（35体を固定し、その敵1体だけを置いて10秒間の「ブレスを吐けていた竜の平均数」を
敵なしの35と比べた値。実際は敵も竜も動くのでこれは上限に近い。）

**射撃型には着弾衝撃（`knockR`）が要った**。弾1発は竜1体しか押せないので、
弾数を9発に増やしても攻撃停止は**2%**しか出なかった。着弾点で小さな衝撃波を起こす
（`projKnockR` / `KNOCK_SHOT_PUSH=52`）ようにして26%まで上がった。

#### (3) 見た目（`KNOCKBACK_MARK_COLOR`）

絵は既存スプライトの流用なので、識別は**共通の標識**が担う。
`def.knockback` を持つ敵に、外へ広がり続ける二重の輪＋4方向のくさびを**常時**描く
（攻撃の瞬間ではなく常時＝近づく前に判断できる）。色はどの文明でも同じ白寄りの水色
`#cfefff`＝「この輪＝押される」を1つ覚えれば済む。
実測: 同じ knights スプライトで、標識なし1描画コマンド → 標識つき7描画コマンド。

#### 負荷

8文明×600フレームの実ループで例外0、更新処理 1.7〜4.8ms/frame。
押してくる敵は大陸あたり7〜12体（石器だけ3人組なので12体＝4組）。

### 2-1j. ノックバック弾を撃つ建物（v0.60）

実機判定（2026-09-03）「ノックバック弾を撃ってくる建物も、強い街やボス周辺にはいるように」。

**衝撃砲台**（`EMPLACEMENT_DEFS.concussionBattery`）を追加した。
弾は移動する「衝撃砲」と同じ仕組み（kind=1 のカタパルト弾＋着弾点の小さな衝撃波 `projKnockR`）で、
4発を扇状に3.2秒ごと・射程470。弾の見た目は `SHOT_STYLES` がその文明のものにする。

#### 置き場所は「格上」だけ

**時代の表（`STAGE_FEATURES[].emplacements`）とは別枠**で配る＝どの文明でも出る。
普通の町には1基も置かない＝「普通の町を焼いているぶんには出てこないが、
格上に踏み込むと押し返される」。

| 置く先 | 数 |
|---|---|
| 首都区画（`_isCapital`） | 3 |
| 要塞都市（`_fixedTier` つき・ボスに近い2〜3町） | 1町につき1 |
| 格上の街（`_tierOffset > 0`） | **3町に1つだけ**（`CONCUSSION_ADVANCED_CHANCE = 0.34`） |
| 普通の町 | 0 |

実測（8文明）: 大陸あたり **8〜12基**（首都3・要塞2〜3・格上3〜6・普通の町0）。
格上の街は大陸に15〜20あるので**全部に置くと20〜26基**出てしまい
「強い街の設備」に見えなくなった（最初の実測）。3つに1つへ絞ってある。

#### 効き目（実測・35体を固定し、砲台の有効/無効だけを切り替えた同一レイアウトのA/B）

| 状況 | 攻撃できていた竜 | 攻撃停止の低下 |
|---|---|---|
| 格上の街で1基（160〜190px） | 35 → 31.2 | **11%** |
| 最終文明の首都区画で3基（190px） | 32.2 → 22.1 | **31%** |

首都の 32.2（砲台オフ）が35に届かないのは、**首都建物のカタパルト弾自体が
押し36.7pxで硬直閾値を超えている**ため（v0.59の設計どおり）。

#### 見た目

移動する押してくる敵と**同じ記号**（外へ広がる二重の輪＋4方向のくさび、色は `KNOCKBACK_MARK_COLOR`）
を `drawEmplacements` でも描く。実測: 焼夷塔2描画コマンド → 衝撃砲台8描画コマンド。
「この輪＝押される」を敵と建物で1つに統一した。

**罠**: `KNOCKBACK_MARK_COLOR` は `drawMovers` の直前（5800行台）で宣言していたが、
`EMPLACEMENT_DEFS`（4400行台）が参照するので **const の TDZ でページが真っ白になる**。
ノックバック硬直の定数群（1100行台）へ移動した。v0.48 で2回踏んだのと同じ罠。

### 2-1k. やられFXと、画面外から来る増援（v0.61）

実機判定（2026-09-03）「竜がやられた時のエフェクトをもう少し目立つように。
ボス周りの移動する敵の湧きが、同じ場所からダンゴになって出てくるので風情がない。
画面外から登場する形にできないか」。あわせて「敵の火力はまだ足りないくらいだが、
細かい調整はいったんこのまま」＝数値バランスには触っていない。

#### (1) やられFX

旧: 0.40秒・半径40の**しぼむ暗いリング**＋灰の火花5〜7個。群れの中で落ちると埋もれていた。
新: **白熱の輪が外へ広がる**＋光条7本＋中心の閃光＋赤白の火花14〜18個。
広がる明るい輪にすると周りの竜より外側へ抜けるので、混戦でも必ず視界に入る。

| | 旧 | 新 |
|---|---|---|
| 表示時間 | 0.40秒 | **0.70秒** |
| リング | 半径40が**縮む**・暗赤/灰 | 半径62まで**広がる**・白熱→赤 |
| 火花 | 5〜7個・40〜120px/s・灰 | **14〜18個**・110〜260px/s・白熱→赤 |
| 光条 | なし | 最初の0.25で7本 |
| 画面揺れ | なし | 2.2 / 0.12秒 |
| 触覚 | 20 | 35 |

出現FX（金・弾ける）と色で対になる（やられ＝白→赤）。
揺れは `triggerShake` が「進行中より強いときだけ上書き」なので、大量にやられても積み上がらない。

#### (2) 増援は画面外から入ってくる

首都の門（中心から150px）に一気に湧かせる方式をやめた。

- 湧く位置は**カメラの視界の外**（群れ重心を中心に、画面の外接円＋余白90px。
  下限640px・上限1150px）。プレビューでは `viewW/viewH` が0になるので下限が効く
- 角度は**首都側の半円（±1.3rad）に等間隔＋ゆらぎ**で散らす＝別々の方向から現れる
- **1組ずつ0.55秒の時間差**で出す
- 隊（packCount 3〜5）は**進行方向に対して横一列**（間隔58px）＝旧の半径42pxの輪をやめた
- **1波は最低3方向**から出す。隊を1つ引くと頭数だけで budget を満たしてしまい、
  結局1か所から出てくることになっていた（実測: 第1波が盾兵4体×1方向だけ）
- 到着まで**行軍速度3.2倍**。群れの260px以内に入るか14秒経つと解除して本来の速度に戻る

実測（電気時代・群れを首都の300px手前に固定・実機相当の390×844）:

| 項目 | 値 |
|---|---|
| 湧いた距離（群れ重心から） | **637〜647px**（画面の外接円は465px＝確実に画面外） |
| 1波の出現方向 | 4〜5方向（26秒で12方向・9回の時間差） |
| 湧いてから群れの250px以内に入るまで | **4.0〜5.4秒**（平均4.5秒） |

**行軍距離の決め方**: 解除を420pxにしていたときは「640→420 の220pxだけ速く走って、
残り420pxを本来の速度で歩く」形になり、コロッサス(26px/s)は接敵まで20秒かかっていた。
260pxまで行軍させると4〜5秒で射程に入る。

負荷: 8文明×900フレームの実ループで例外0、更新処理 1.1〜3.4ms/frame。

**次にやるなら**: 画面外の増援がどちらから来るか、画面端に小さな指標を出す案
（非モーダル）。今は「端から入ってくるのを見る」だけなので、背後から来られると気づけない。

### 2-1l. 通常弾を1/3の速さに（v0.62）

実機判定（2026-09-04）「敵の通常弾の速度が速すぎて見た目がイマイチ。1/3くらいにすると
敵の攻撃の激しさが目に見えていい。弾が多すぎて処理落ちする？　ロケット弾とかの見た目はいい感じ」。

**通常弾（kind=0 矢 / kind=1 カタパルト弾）だけ 1/3**にした（`NORMAL_SHOT_SPEED_SCALE`）。
ロケット(kind=3)・ボス重弾(kind=2)・着弾弾(kind=4)は見た目が良いので**触っていない**。
弾は飛距離で消えるので、遅くしても届く範囲は同じで**滞空時間だけが3倍**になる。

#### 処理落ちするか → しない（実測）

同じ場面（最終文明の首都・竜55体・390×844・カメラ固定）で、
`NORMAL_SHOT_SPEED_SCALE` だけを 1 と 1/3 に差し替えたA/B:

| | 現行速度 | **1/3速** |
|---|---|---|
| 平均同時弾数 | 51.6 | **167.2** |
| 最大同時弾数 | 190 | **507** |
| 画面内の平均 | 41.6 | 124.1 |
| `updateProjectiles` | 0.19ms | **0.41ms** |
| `drawProjectiles` | 0.27ms | **0.61ms** |
| それ以外の更新 | 9.28ms | 9.30ms |

弾まわりは 0.46ms → **1.02ms**（1フレーム16.6msのうち）。
**重いのは弾ではなく群れ・敵・建物の更新（9.3ms）**で、そこは1/3速でも変わらない。
8文明の実ループでも 6.4〜10.2ms/frame（最重量は大戦の10.2ms＝敵165体のぶん）。

#### プールは 200 → 900 に広げた（必須）

滞空時間が3倍になるので同時数も3倍になる。`spawnProjectile` は**空きが無いと黙って何もしない**
ので、200のままだと撃った弾が消える。実測の最大は 642（竜が動く条件）なので 900 にした。
あわせて空きスロット探索を**巻き取り式**（`takeProjectileSlot`）にした。
毎回先頭から舐めると発射1回につき最大900回の走査になるため。

#### 敵の火力は 14% 落ちる

同じ場面で20秒間に竜が受けた合計ダメージ: **24,265 → 20,900（-14%）**。
弾が遅いぶん避けられるが、被害の多くは持続範囲攻撃・衝撃波・レーザー・着弾AoEなので
下がり幅は限定的。Shooter は「敵の火力はまだ足りないくらい」と判断済みなので**据え置き**。
戻したくなったら建物の発射間隔（`projectileInterval`）を詰めるのが素直。

### 2-1m. 弾の威力・旋回性能・巨人型・範囲攻撃の出どころ（v0.63）

実機判定（2026-09-04）「弾幕が演出として機能するようになった。回避できそうな感触も良い。
弱くなった分は弾丸の威力を30%上げて。船や車両っぽい見た目の敵は旋回速度を下げて。
巨人型は横移動もして、前面に苛烈な攻撃・旋回は60度単位のみ、みたいにするとメリハリが出そう。
円形の予兆あり範囲攻撃は誰が撃ってるか分からないので、当たり判定のない弾を飛ばして」。

#### (1) 通常弾の威力 +30%

`NORMAL_SHOT_DAMAGE_MULT = 1.3` を**直撃ダメージのうち kind=0/1（矢・カタパルト弾）だけ**に掛ける。
実測: 矢 4.3 → **5.59** / カタパルト弾 4.3 → **5.59** / ボス重弾 4.3（据え置き）/ ロケット 4.3（据え置き）。
v0.62 の -14% を埋めて釣りが来る計算。

#### (2) 向きの作り方を3種類に分けた

v0.62 までは**全員が進みたい方向へ即座に向く**ので、船や車両がその場で回れ右をしていた。

| 種類 | 挙動 | 対象 |
|---|---|---|
| 既定 | 目標方向へ即座に向き、その方向へ進む | 歩兵・獣・飛行 |
| `turnRate` | 旋回角速度に上限。**向いている方向にしか進めない**＝行き過ぎたら大回り | 船・車両11種 |
| `stepTurn` | 向きは60度刻み。**移動は目標方向のまま**＝横歩き・後ずさりが出る | 巨人型2種 |

旋回半径 = 速度 ÷ turnRate:

| 敵 | turnRate | 旋回半径 |
|---|---|---|
| 装甲列車 | 0.45 | **89px**（一番曲がれない） |
| 陸上甲鉄艦 | 0.55 | 55px |
| 殲滅砲兵 | 0.50 | 44px |
| ウォーロード / 破城槌 / 衝撃砲 | 0.60 | 40〜43px |
| 散弾砲車 | 0.65 | 46px |
| 火吹き車 / 雷撃塔車 | 0.85 | 38〜40px |
| 牡牛戦車 | 1.10 | 47px |
| 財宝馬車 | 1.20 | 67px（逃げ足は残す） |

実測: 甲鉄艦の1フレームあたりの向き変化は上限 0.0092rad ちょうどで頭打ち（0.55/60）。
絵が回らないもの（`forward:"none"`＝気球・分裂体・召喚門・治癒塔・攻城塔）は
見た目に出ないので付けていない。

#### (3) 巨人型（コロッサス／黄金の巨像）

- 向きは**60度刻み**の6方向のみ。移動は目標方向のままなので**横歩きする**
- 踏み替えは目標方向が **60度**ずれてから（`STEP_TURN_HYSTERESIS = 1.05`）。
  36度で試したら向きと進行方向のずれが平均15度しか出ず、横歩きに見えなかった
- ビームは**正面±35度**（`frontArc`）にしか通らない。そのぶん苛烈に（5.0→8.5 / 9.0→15.0）

実測（群れを敵の周りに1周させた720フレーム）:

| | 値 |
|---|---|
| 出た向き | -120/-60/0/60/120/180 の**6方向だけ** |
| 向きと進行方向のずれ | 平均**30度**・最大60度 |
| はっきり横歩き（40度以上ずれ） | 移動フレームの**33%** |
| ビームが出ていた割合 | **62%**（38%は正面から外れて撃てない） |
| 12秒の与ダメージ | 113（旧構成の理論値108とほぼ同じ＝総量は据え置き、出方がメリハリに変わった） |

#### (4) 範囲攻撃の「見せ弾」

`spawnHazard` に発射元 `fromX/fromY` を足し、**当たり判定のない見せ弾**を飛ばす
（`hazardShots` / `spawnHazardShot` / `drawHazardShots`）。
飛行時間は予告時間 `HAZARD_WARN_TIME=0.7秒` ちょうど＝**着弾と同時に燃え始める**。
トップビューなので高さが出せない。地面を進む影と、法線方向へ膨らませた弧の2つを描いて
「山なりに飛んできた」を表す。

実測:
- 火吹き車（300px先の群れを狙う）: 見せ弾が frame 1 に発生 → **frame 43 で最初のダメージ**
  （予告42フレーム＋1＝着弾と同時）
- 瘴気塔（自分の足元に置く型）: 見せ弾**なし**（出どころが自明なので飛ばさない。60px以内は省略）
- 古代の首都「神託の光柱」: 首都から**7発**が461px先の各柱へ飛ぶ
- 描画は1発あたり4コマンド（影・もや・芯・ハイライト）

負荷: 8文明×420フレームの実ループで例外0、6.9〜9.4ms/frame、弾の最大473（プール900）。

### 2-1n. 見せ弾の拡大・貫通弾・全方位の整理（v0.64）

実機判定（2026-09-05）「範囲攻撃の見せ弾はいい感じなのでもっと大きく。ノックバック弾は
着弾で範囲攻撃になるものの他に、当たっても消えず多段ヒットするもの（代わりに衝撃波なし）も
用意していろんな敵・建物・ボスに使わせて。連発や弾幕が良い。全方位攻撃の建物は多用すると
面白くないので減らす（ボスや各街の中央の建物は良い）。全方位の球は弾速を遅く、
旋回しながら撃つ感じで通常弾と差別化して」。

#### (1) 見せ弾を大きく

弾の大きさを**置かれる危険地帯の半径に比例**させた（0.9〜2.1倍でクランプ）。
大きい輪ほど大きい塊が飛んでくる＝着弾前に規模が読める。
本体は芯7.5px＋外光20px（旧: 芯4.2px＋外光9px）に拡大し、尾を3つ、
影は高度で伸縮するようにした。描画コマンドは1発 4 → **8**。

実測の倍率: 火吹き車(r110)=1.16 / 瘴気(r230)=**2.10** / 光柱(r74)=0.90。

#### (2) 貫通弾（`projPierce`）

**当たっても消えず、群れを貫いて多段ヒットする**。代わりに着弾衝撃（`projKnockR`）を持たない。
連続ヒットの刻みすぎを防ぐため `PIERCE_HIT_INTERVAL = 0.09秒` の待ちを入れてある。

- 着弾型（衝撃砲台・散弾砲車）＝「**円から退く**」課題
- 貫通型＝「**線から出る**」課題を長く突きつける

使わせた先（Shooter指示「いろんな動く敵や建物、ボスに」）:

| 使い手 | 内容 |
|---|---|
| 🚄 装甲列車（動く敵） | 舷側砲4連を貫通弾に。走りながら群れを串刺しにする |
| 📣 衝撃砲（動く敵） | 着弾衝撃をやめて貫通5連射に（散弾砲車と対になる） |
| 🏹 連装貫通砲（建物・新規） | 3発を細い扇で2.4秒ごとに連射。要塞都市1／首都2 |
| 👑 首都の一斉射（近世のボス技） | 13発×3波の壁が貫通弾に。通り過ぎるまで線から出続ける必要がある |

実測（一直線に並べた竜へ1発）: 通常弾は1体に当たって消える（5.6ダメージ・23フレームで消滅）。
貫通弾は**8体に当たり89.4ダメージ、240フレーム後もまだ飛んでいる**。
現実的な条件（35体・10秒・射程の75%）では 衝撃砲台67 に対し **連装貫通砲391**（間隔2.1のとき）。
他の兵器（投石機340・臼砲246）より頭一つ高かったので間隔を2.4へ緩めた。

#### (3) 全方位攻撃を「ボスと町の中央」だけに

`projectileCount >= 4` の建物（近世・産業・最終の medium/large 全部）が全方位に撒いていて、
どこを焼いても同じ花火が上がり続けていた。**ボスと町のランドマーク（神殿/風車）だけ**に絞った。

| 文明 | 全方位を撃てた建物 | → 撃てる建物 |
|---|---|---|
| 近世要塞 | 757 | **61** |
| 産業 | 2040 | **61** |
| 最終 | 2225 | **66** |

撃たなくなった建物は**狙い撃ちの2連射**に落ちる（撒くのをやめただけで沈黙はしない）。

> **v0.64.1 で量は元に戻した（Shooter判断）。**
> 実機で「弾丸の演出がショボくなった」。原因は**弾幕の性質が均一化したこと**。
> 全方位は「面で降ってくる別種の圧」で、狙い撃ちの弾と混ざることで密度に濃淡が出ていた。
> ＝**撃つ建物の数が多いこと自体が弾幕の質**だった。
> `canFireOmni` を `projectileCount >= 4` に戻し、近世770／産業2069／最終2263棟が撃つ。
> **見た目の差別化（遅い球・旋回・共通の球で描く）はそのまま残している**ので、
> 「量は元どおり、質は別物」という形になった。
> 実測（最終文明の首都に45体・HPを毎フレーム戻して600フレーム）:
> 同時弾272発（うち球51〜123発）・**攻撃できていた竜は57%**（＝押されっぱなしにはならない）・
> 更新1.15ms/frame・プール満杯フレーム0（最大480/900）。
> 絞りたくなったら `canFireOmni` を `isBoss || _landmark` に戻すだけで効く。

撃つ側は**遅い球を旋回しながら撒く**:
- 速度は通常弾のさらに 0.55 倍。実測 **238px/s（同じ建物の通常弾は432px/s）**
- 斉射ごとに基準角を `OMNI_SPIN_STEP = 0.42rad` ずらす。実測で1.40→1.82→2.24→2.66→3.08 と
  **毎回きっかり0.42ずつ回る**＝風車のように見える
- 描画も文明の弾スタイルではなく**共通の球**（脈打つ外光＋芯＋回転する白い弧）
  → **v0.65.2 で撤回**。全時代で同じ光る玉になり「v0.62 より見た目が劣化した」（Shooter判断）。
  弾の形は時代を語る面積なので、共通化してはいけない箇所だった。
  形は `SHOT_STYLES` に戻し、**背後に薄い暈（うん）を敷いて 1.75 倍で描く**ことで
  「別枠の攻撃」だと分かるようにした。挙動（遅い・斉射ごとに0.42rad旋回）は据え置き。
  実測: 全方位弾の描画コマンド数が **通常弾＋2（暈のぶん）** になり、
  投石2→4・投槍3→5・弩矢4→6・鉛玉3→5・榴弾5→7・放電弾3→5・曳光弾2→4・プラズマ4→6 と
  **時代ごとに違う形**で描かれていることを確認（v0.64 は全時代とも一律3コマンド）。

#### 差し引きの火力

首都に55体で20秒張り付いた同一条件の比較:

| 版 | 20秒の被ダメージ |
|---|---|
| v0.61（弾が速い） | 24,265 |

### 2-1u. 建物が真っ黒になるバグ（v0.72）

実機で「時々真っ黒の建物がある。意図的か？」（2026-09-05）。**バグ**だった。

#### 原因

`shadeColor` が **`#rrggbb` しか読めなかった**。
建物の色は生成時点で既に `shadeColor` を通っていて **`rgb(r,g,b)` 形式**になっているのに、
動員段階の色締めがもう一度 `shadeColor` に渡していた。

```
parseInt("rgb(90,48,24)", 16)  →  NaN
(NaN >> 16) + amount           →  0 + (-40)  →  clamp  →  rgb(0,0,0)
```

**try/catch では捕まらない**（例外ではなく NaN が返るだけ）ので、静かに真っ黒を返していた。
そこへ無彩色スプライトの multiply ティントが掛かるので、建物が**塗り潰しの黒い矩形**になる。

実測（修正前）: 真っ黒な建物が **大陸あたり 1300〜2100棟＝全建物の16〜27%**。
内訳は**格上の街と要塞都市だけ**＝色締め（`TIER_SHADE_STEP`）を通る建物すべて。
v0.56 から入っていたので、**「格上の街は色が締まって見分けられる」も実は機能していなかった**
（見分けられていたのではなく、黒く潰れていた）。

#### 直し方

1. `parseColorRGB` を追加して **`#rrggbb` と `rgb(r,g,b)` の両方**を読む。
   読めない形式は**入力をそのまま返す**（黒に潰さない）
2. 建物の色締めだけ `shadeBuildingColor` に分け、**元の色に対する比**で下限を入れる
   （`BUILDING_SHADE_MIN_RATIO = 0.55`）。
   絶対値の下限にすると、元から暗い文明（最終文明の `#2a2a2a`）では
   下限のほうが明るくなり「格上の街のほうが明るい」と逆転するため。
   地面・街道の `shadeColor` には下限を掛けない（あちらは暗いのが正しい）

実測（修正後）: **8文明すべてで真っ黒な建物0**。動員段階を2つ上げても0。
地面の色は変化なし（`shadeColor("#0d1a08", -8)` → `rgb(5,18,0)` で修正前と同じ）。

**教訓**: 色を「文字列で持って何度も変換する」経路は、途中で形式が変わると静かに壊れる。
`parseInt(..., 16)` は例外を投げずに NaN を返すので try/catch では守れない。

##### v0.84: 前哨堡に向きを付ける

実機指示（2026-09-13）:「攻撃は前方向のある程度限った角度に。建物の見た目も指向性がある見た目に。

### 2-1aa. 特殊個体（v0.85）

Shooter 指示。「ラン中の強化として、母竜とは別の役割持ちを群れに加える」。
**ラン開始時に選ぶのは竜種だけ**（既にある）。特殊個体は**ラン中に引いて加入**させる。
総称は「特殊個体」（「母」を共通名にしない、という指示）。

#### 決めたこと

| 項目 | 決定 |
|---|---|
| 加入 | ラン中の★カード。1枚で1匹加わる（群れの数は減らない） |
| 同時加入数 | **初期3体**。恒常ツリー「変わり者の座 / 異端の群れ」で +1 ずつ |
| 枠が満杯 | 加入カードはプールから消える。強化カードは**連れている種類のぶんだけ**出る |
| ステージ遷移 | 持ち越す（スロット1以降に割り当て直す）。ランをまたぐと消える |
| ダウン中 | 母竜と同じく能力ごと消える（呑竜は溜めた弾も失う） |
| 名前 | 灯竜（beacon）／巌竜（heavy）／呑竜（deflect） |

#### 3種

**灯竜** — 自分の周りを回る光条（長さ150px）。触れたものが焼ける。
角速度は「進行方向からのずれ」で決まり、前を向いている間は遅く、後ろ向きでは速い
＝**直進すると前で粘り、旋回すると薙ぎ払いになる**。なぞる線の形が攻撃の形になる枠。

**巌竜** — **遠隔攻撃を一切持たない**。体当たりだけで建物を砕く。体格1.5倍＋レベル成長、
HP3倍、ノックバックもヒットストップも受けない。塊魂の柱に直結する枠。

**呑竜** — 自分の周り70pxに来た**通常弾（矢・カタパルト弾）だけ**を吸って溜める。
満杯（10発）から1.5秒後に前方へ束にして撃ち返し、その後3秒は吸えない。
レーザー・着弾弾・ロケット・ボス重弾は**吸えない**ので、避ける種類の攻撃はそのまま残る。

| 測ったこと | 結果 |
|---|---|
| 灯竜の1回転（自由飛行） | 0.35/2.20 rad/s で **5.31秒** → 1.00/2.80 rad/s で **3.76秒**（採用） |
| 灯竜の1回転（街の中で旋回中） | 5.65秒 → **3.61秒** |
| 灯竜の与ダメージ | **25.3 dps**（街の中。複数棟を同時に薙ぐため基礎18より高い） |
| 巌竜の与ダメージ | **62.3 dps** / 8秒で16棟破壊。同条件の通常個体は 16.0 dps / 3棟 |
| 巌竜の遠隔攻撃 | ブレス射程内（68px）に置いて **8秒で0ダメージ**（通常個体は同条件で1棟破壊） |
| 呑竜の吸い込み率 | 群れ34体を街に密集させて **17.1%**（吸12発 / 竜に着弾58発） |
| 呑竜の周期 | 16秒で3回発射（0→10→発射→クールダウン3秒→0→10…）が安定して回った |
| 負荷 | 特殊個体8体＋弾200発の最悪ケースで **0.32 ms/frame**（弾は実運用で20〜40発） |

**灯竜の回転は最初 0.35/2.20 rad/s で作ったが、旋回中は進行方向に捕まり続けて実質静止して見えた**
（ピン留め計測で1回転10.5秒）。「回る光条」という読み取りが壊れるので下限を引き上げた。
前で粘る性質は 2.8 倍の差として残している。

#### 実装の差し込み口

- 種別と定数: `SPECIAL_NONE/BEACON/HEAVY/DEFLECT`、`SPECIAL_DEFS`（名前・色・HP倍率）。
  **`CARD_DEFS` の初期化子が `specialJoin: SPECIAL_BEACON` を参照するので、
  この定数ブロックだけは boid 配列の宣言と同じ位置（CARD_DEFS より前）に置いてある**（TDZ 対策）。
- 状態: `boidSpecial` / `boidSpecialAngle`（光条の向き）/ `boidSpecialStock`（溜め弾数）/
  `boidSpecialTimer` / `boidSpecialCd`。ラン内の加入履歴は `runSpecials`。
- 加入: `addRunSpecial(kind)` → 空きがあれば新しい竜として増やし、満員なら通常個体を1匹転じる。
  ステージ開始の再配置は `applyRunSpecials()`（`resetBoidsForStageStart` の末尾）。
- 更新: `updateSpecials(dt)`（`updateWeaponAttacks` の末尾）→ `updateBeaconDragon` /
  `updateHeavyDragon` / `updateDeflectDragon`。弾は `sbolt*` プール＋`updateSpecialBolts`。
- 吸い込み: `tryDeflectAbsorb(projIdx)` を `updateProjectiles` の当たり判定の直前で呼ぶ。
  **弾1発ごとに呼ばれるので群れ全体を走査させない**（`deflectSlots` を毎フレーム作り直して
  呑竜のスロットだけ見る。弾900×群れ150 を避けるため）。
- 遠隔攻撃の除外: 各武器ループの先頭に `if (boidSpecial[i] === SPECIAL_HEAVY) continue;`。
  **`updateCollisionAttacks` には入れない**（巌竜はそこを通る必要がある）。
- 体格: `boidBodyScale(i)` に母竜の成長と巌竜の巨体を一本化。描画と衝突半径の両方がこれを使う。
- 描画: `drawSpecialUnder`（光条・足元リング・吸引域）→ `drawBoids` →
  `drawSpecialOver`（溜め弾の周回球）→ `drawSpecialBolts`（撃ち返した弾）。
- 移動敵の半径は **`m.def.radius`**（`m.radius` は存在しない）。`moverRadiusOf(m)` を用意した。

#### 残した調整つまみ

灯竜: `BEACON_DPS 18` / `BEACON_LENGTH 150` / `BEACON_SPIN_MIN 1.00` / `MAX 2.80`。
巌竜: `HEAVY_RAM_DAMAGE 60` / `HEAVY_RAM_COOLDOWN 0.40` / `HEAVY_SCALE 1.5`。
呑竜: `DEFLECT_RADIUS 70` / `CAPACITY 10` / `HOLD 1.5` / `COOLDOWN 3.0` / `BOLT_DMG 20`。
枠: `SPECIAL_SLOTS_BASE 3`。ツリー: 枠 +1 が 130/240 竜晶、威力 +25% が 110 竜晶。

**巌竜が 62 dps と3種で一番高いのは、遠隔攻撃をまるごと捨てていて
1棟ずつ物理的に触りに行く必要があるため**。灯竜と呑竜は通常のブレスを撃ち続ける。

### 2-1ab. 群れの計測（v0.86）

Shooter 指示。「群れを使った新しい攻撃要素を検討したい。まず重心の速度と向き、
それと群れのばらつきを毎フレーム計測してデバッグ表示する」。
**攻撃そのものはまだ作っていない。条件に使える数値を先に用意した段階。**

#### 出している数値

`flockMetrics` を `simStep` の末尾で毎フレーム更新する。simStep は playing 以外
（title・クリア演出）でも通るので、どの状態でも値は生きている。

| 表示 | 中身 | 使いどころ |
|---|---|---|
| 重心速度 | 個体速度の平均の大きさと向き | 「どれだけ勢いがあるか」。突進系の条件 |
| 旋回 | 重心の向きの変化率（°/s） | 曲がっている最中かどうか |
| 広がり | 重心からの距離のRMS（σ）と最遠個体まで | 「固まっているか散っているか」 |
| 縦横 | 進行方向の広がり / 横方向の広がり | **>1で槍、<1で壁**。形そのものを条件にできる |
| 整列度 | 速度の向きだけを平均した長さ（0..1） | 1=全員同じ方向。Vicsek の秩序変数 |
| 旋回度 | 重心から見た外向きと進行方向の外積の平均（-1..1） | **群れ自身の重心のまわりを回っているか**。+が反時計回り |
| 最近接 | 最近接距離の平均と最小 | 密度。広がりと組で「大きいのか詰まっているのか」が分かる |
| 速さのばらつき | 個体の速さの標準偏差 | 伸びているか揃っているか |

**重心速度は位置の差分ではなく平均速度で出している。** 卵で竜が増えた瞬間や
ダウン復帰で母集団が変わると差分は飛ぶため。合成データで検証したところ、
平均速度と重心位置の差分は float32 の丸め（105.5000 と 105.5002）まで一致した。

**整列度と旋回度を分けているのが要点。** 「揃っている」と「回っている」は別物で、
2つ組で見ると群れの状態が3つにはっきり割れる（実測）。

| 局面 | 重心の速さ | 整列度 | 旋回度 | 縦横 | 広がり |
|---|---|---|---|---|---|
| 直進（指を前に置く） | 147 | 0.99 | -0.02 | 2.27 | 94 |
| 円を描いて移動 | 159 | 0.99 | 0.04 | 1.07 | 51 |
| 指を止める（その場で渦） | 75 | 0.50 | 0.46 | — | 93 |

**「円を描いて移動」で旋回度が上がらないのは正しい。** 旋回度は
*群れ自身の重心のまわりの回転* を測るので、群れごと円周上を移動しても0に近い。
上がるのは指を止めて群れがその場で渦を巻いたときだけ。
一方で直進すると縦横が 2.27 まで伸びる（＝線に沿って槍の形になる）。

#### 既知の配置での検証

| 与えた配置 | 整列度 | 旋回度 | 縦横 |
|---|---|---|---|
| 全員同じ向きに直進 | 1.00 | 0.00 | 1.53 |
| 向きがばらばら | 0.02 | -0.01 | 1.09 |
| 完全な反時計回りの渦 | 0.00 | **+1.00** | 1.00 |
| 完全な時計回りの渦 | 0.00 | **-1.00** | 1.00 |
| 進行方向に一列（槍） | 1.00 | 0.00 | **33.2** |
| 進行方向と直角に一列（壁） | 1.00 | 0.00 | **0.03** |

重心・広がり・整列度・最近接は、実プレイ中の値をブルートフォース計算と突き合わせて
**小数3桁まで完全一致**を確認した。

#### 表示

- ワールド座標（`drawFlockMetricsWorld`）: 重心の十字／速さに比例する黄色い矢印／
  進行方向を長軸にした破線の楕円（広がり）／最遠個体までの薄い円／
  旋回度が 0.12 を超えたときだけ出る弧（緑=反時計・桃=時計）。
- スクリーン座標（`drawFlockMetricsPanel`）: 左上の数値パネル。整列度と旋回度は棒でも出す。
  **`#hud-left` が x8..72 / y0..88 を占めるので、パネルは y=96 から置く**
  （パネルは canvas、HUD は DOM なので重ねると HUD に隠れる）。
- デバッグメニュー「📊 群れの計測」でON/OFF。既定ON。
- **重心速度は小数第2位まで**出す（v0.86.1・Shooter指示）。表示値は 0.18秒の指数平滑をかけているので、生の値を見たいときは `flockMetrics.speed` を直接読む。

#### 負荷

150体での実測。

| | ms/frame |
|---|---|
| O(n) の2周（重心・広がり・整列度・旋回度・縦横） | 0.022 |
| 最近接距離を足すと | 0.18 |

**最近接距離だけで全体の88%を食う**ので、表示中のみ計算する
（`debugShowFlockMetrics` で分岐）。他の値はゲーム側から使う前提なので常に更新する。
最近接は `simStep` が作る群れの空間ハッシュ（セル55px）を流用して 3x3 セルだけ見る。
グリッドは位置更新の**前**の座標で作られているが、1フレームの移動は数pxなので
165px の窓から真の最近接がこぼれることはない。窓の中に誰もいない**はぐれ個体だけ**
全走査に落として値を正しく保つ（この保険が無いと散開時に値が過小になる）。

#### 次にやること

この数値を条件にした攻撃要素はまだ入れていない。組み合わせの候補としては
「整列度が高いときだけ発動する突進」「旋回度が高いと渦の中心に何かが生まれる」
「縦横が大きい（槍）ときに貫通が伸びる」あたりが素直。**どれを作るかは未決定。**

### 2-1ac. 突進（v0.87）

Shooter 指示。「群れの重心速度が竜の最高速度の 99.5% 以上のとき突進状態になる。
直接攻撃の威力が上がり攻撃範囲が増え、動く敵にはノックバックも与える。
維持すると 2 秒で上限まで大きくなる。しきい値も 2 秒も伸び幅も、竜種と強化で変わるようにする」。

v0.86 で作った `flockMetrics` の最初の使い道。

#### なぜ「重心速度」が条件として効くのか

重心速度は個体速度の**平均ベクトル**なので、全員が最高速でも向きがばらけていれば小さくなる。
つまり 99.5% という条件は速さだけでなく**揃い方**も同時に要求する（整列度が1に近くないと物理的に届かない）。
「線を前に引いて群れを一本にまとめる」という操作がそのまま発動条件になっている。

#### 到達可能性（実測・38体・火竜）

| 操作 | 平均速度比 | 99.5%以上だったフレーム | 到達した溜め |
|---|---|---|---|
| 指を群れの前に置いて直進 | 99.9% | **100%** | 100% |
| 大きく円を描く | 96.7% | 52.5% | 100% |
| 小さく円を描く | 99.3% | 36.9% | 100% |

**直進すればほぼ常時、曲がると半分以下**。狙って出せるが、旋回すると落ちる。
なお最初に別パターンで測ったときは 91.7% しか出なかったが、あれは操縦点を固定していたため
到達減速（`LEADER_ARRIVAL_DIST`）が効いていたもので、指を前に置き続ける本来の操作では届く。

#### 効果（実測・38体・大型建物）

| | dps | 突進の維持率 |
|---|---|---|
| 接触距離・突進なし | 259 | 0% |
| 接触距離・突進あり | **1,095** | 91% |
| 接触の 15px 外・突進なし | 0 | 0% |
| 接触の 15px 外・突進あり | **339** | 100% |

倍率の定義は ×3.0 だが実測比は **4.23 倍** だった（この測定は `plowThrough: true` 時のもので、
止まらないぶん体当たりの回数が増えていた）。**15px 外で 0 → 339 は範囲ボーナスが効いている証拠**。

ノックバックは溜めに比例する（レイダー・2秒・押した向きの変位）。

| 溜め | 変位 | ノック速度の最大 |
|---|---|---|
| 0% | -160px（敵が自力で歩いた分） | 3 |
| 50% | +143px | 156 |
| 100% | +441px | 306 |

#### 作っている途中で直した2つ

**① ノックバックが群れの数だけ積み上がっていた。**
`updateMoverRams` は射程内の竜が**全員それぞれ**体当たりするので、37体が同じフレームで押すと
1体ぶんの37倍の速度になった（実測: 3秒で 9,676px 吹き飛んだ。想定は数十px）。
`MOVER_KNOCK_STACK_CAP = 1.8` で1発ぶんの1.8倍を上限にした。大群のほうが速く押せるが青天井ではない。

**② 「ヒットストップで突進が切れる」と判断して `plowThrough` を入れたが、その判断自体が誤りだった。**

最初の計測で維持率 33%・平均溜め 0.11 しか出ず、ヒットストップが原因だと考えて
「突進中はヒットストップを受けない」を既定にした。しかし simStep を読み直すと
**ヒットストップは位置更新だけを飛ばし、速度ベクトルは維持する**仕様だった
（`if (boidHitStopped[i] > 0) continue;` は操舵と積分を丸ごと飛ばす）。
重心速度は vx/vy の平均なので、**ヒットストップでは一切落ちない**。

33% は計測側の欠陥だった。竜を建物の周りにピン留めして速度を 16ms ごとに上書きしていたため、
シム側の操舵と争って向きが散っていただけ。

実際の街を貫通する形で取り直した結果（建物数の近い4つの街・同じ助走）:

| | 街 | 建物 | 破壊 | 与ダメ | 街の中での維持率 |
|---|---|---|---|---|---|
| 貫通あり | 9 | 85 | 74 | 1,345 | **100%** |
| 貫通なし | 11 | 92 | 91 | 1,364 | **100%** |
| 貫通なし | 12 | 73 | 64 | 1,098 | **100%** |
| 貫通あり | 20 | 97 | 91 | 1,433 | **100%** |

**どちらでも街の中で維持率 100%**。破壊数にも有意差はない。
よって `plowThrough` は **v0.87.1 で既定 false（＝従来通り止まる）に戻した**。
パラメータ自体は「突進中は止まらない」を試すつまみとして残してある。

**教訓:** 群れの挙動を計るときに位置や速度を外から固定すると、
シムの操舵と競合して**実プレイと違う数字**が出る。判断に使うなら実操作相当で測る。

#### 調整できるもの

竜種は `SPECIES_DEFS[x].charge` で `CHARGE_PROFILE_DEFAULT` を部分上書きする（`mv()` と同じ作り。`chg()` で引く）。

| 項目 | 既定 | 意味 |
|---|---|---|
| `enterSpeedFrac` | 0.995 | 突進に入る重心速度（実効最高速度に対する割合） |
| `exitSpeedFrac` | 0.985 | 抜ける割合。**入りと同値にすると境界で毎フレーム点滅する** |
| `rampSeconds` | 2.0 | 上限まで溜まる秒数 |
| `decaySeconds` | 0.5 | 切れた後に溜めが0へ戻る秒数 |
| `damageMult` | 3.0 | 最大溜めでの直接攻撃の威力倍率 |
| `reachBonus` | 22 | 最大溜めで当たり半径へ足す px。倍率でないのは建物半径が 6〜28px とばらつくため |
| `knockback` | 190 | 最大溜めで移動敵を弾く初速 px/s |
| `damageReduction` | 0 | 突進中の被ダメージ軽減。0 より大きいと衝角波が丸い弧になる。上限 `CHARGE_GUARD_MAX = 0.75` |
| `plowThrough` | **false** | true にすると突進中はヒットストップを受けなくなる（維持には不要だと実測で確認済み） |
| `fxScale` | 1.0 | エフェクトの大きさ（当たり判定には影響しない） |

竜種の上書きを3種に入れてある。

| 竜種 | 上書き |
|---|---|
| 緋竜 | ×4.2 / 範囲30 / 押240 / fx1.2（体当たりが主武装なので伸びが一番大きい） |
| ガーゴイル | 溜め2.8s / ×3.4 / 押320 / **軽減0.15**（石の竜なので素で軽減を持つ＝この種だけ最初から盾の形） |
| UFO | 入0.998 / 抜0.992 / 溜3.0s / ×2.2（`minSpeed === maxSpeed` で常に全速なので入りやすすぎる。しきい値を上げて釣り合いを取る） |

強化は `eff*` 経由。実測で全項目が動くことを確認した。

| | 素 | ラン中カード（ease2/ramp2/dmg3/reach2） | ＋ツリー3種 |
|---|---|---|---|
| 突入しきい値 | 0.995 | 0.975 | 0.960 |
| 溜め時間 | 2.00s | 1.28s | 1.02s |
| 威力倍率 | ×3.0 | ×5.1 | ×6.33 |
| 範囲 | 22px | 35.2px | — |
| 被ダメ軽減（v0.89） | 0% | 15%（カード1枚） | 60%（カード3枚＋ツリー） |

しきい値には下限 `CHARGE_ENTER_FRAC_MIN = 0.90` を置いてある（下げすぎると常時突進になるため）。
**しきい値は実効最高速度（`mv().maxSpeed × effSpeedMult()`）と比べる。**
素の maxSpeed と比べると「疾風の翼」を取っただけで常時突進になってしまう。

#### 見せ方（v0.88 で作り直した）

**v0.87 の「群れの先端の弧」と「重心から後ろへ流れる速度線」は廃止した。**
Shooter から「これはデバッグ表示ですか、それともエフェクトですか」と問われた＝
**重心に描く図形は竜と紐づかないので図解に見える**。エフェクトとして機能していなかった。

代わりに、すべてを個体に紐づける。

| 何を | どこに | 意味 |
|---|---|---|
| 尾を引く線 | 各竜の後ろ | 全員が同じ向きに走っている |
| **衝角波（bow wave）** | 各竜の少し前に弧 | 竜1匹ずつが空気を押している。40体分が並ぶと衆波の壁になる |
| **突進ヒット** | 当たった点 | 突進が乗った一撃だけに出る専用の衝撃 |

衝角波は外側（柔らかいにじみ・青白）と内側（明るい芯・白）の二重。半径は `9 + 11 × 溜め`。竜のスプライトを覆わないよう、中心を進行方向へ 30% ずらす。

**v0.89: 衝角波の形が被ダメージ軽減の有無を兵ねる。**
丸い弧はバリアに見える（Shooter 指摘）ので、それを逆に利用して意味を乗せた。

| 軽減 | 形 | 読み |
|---|---|---|
| あり（`charge_guard` 系を取っている） | 丸い弧 | 守っている |
| なし（既定） | 尖った「〉」 | 貫くだけで守らない |

尖った形は `lineJoin: miter` / `lineCap: butt` で先端を死なせない。

**v0.89.1: 先端の内角を直接持つ形に直した。** v0.89.0 は「腕を何度後ろへ振るか」（`CHARGE_CHEVRON_SWEEP = 2.25`）で指定していたが、その形だと先端の内角が実際には **44度** になり、腕が竜の上まで巻いていた（Shooter指摘）。指定と見た目が一致しない形だったのが原因。

| | 値 |
|---|---|
| `CHARGE_CHEVRON_ANGLE` | 2.094 rad（**120度**・先端の内角） |
| `CHARGE_CHEVRON_TIP` | 0.90（先端を bowR の何倍前へ置くか） |
| `CHARGE_CHEVRON_ARM` | 1.15（腕の長さの bowR 比） |
| `CHARGE_CHEVRON_WIDTH` | 0.85（尖った形だけ線を細くする倍率。丸い弧は等倍のまま） |

腕の後方成分は `armLen × cos(60°) = 0.5 × armLen` なので、腕の末端も竜の中心より前に残る。実測では溜め0% で 5.6px 前、溜め100% で 12.5px 前。

角度は 135度（v0.89.1）→ **120度**（v0.89.2）。135 は鈣角すぎたという Shooter 判定。
線の太さも 0.85 倍に絞った（外 7.0→5.95 / 内 3.0→2.55）。

突進ヒット（`spawnChargeHitFx` / `drawChargeHitFx`）は**通常の体当たり（`spawnCollisionParticles`）と
見分けられること**が目的。破片が飛ぶだけでは「突進が効いた」が伝わらないので、
進行方向に開く暖色の弧＋放射状の裂け線＋白い点にした。色で寒色（衝角波）と暖色（ヒット）を分けている。
大きさは `0.35 + 0.65 × 溜め` 倍。移動敵に当たったときは画面揺れも `1.6 + 1.6 × 溜め` で乗る。

突進が切れて溜めの余韻だけのときは不透明度を 0.45 に落とす（効いていないのに派手だと嘘になる）。
計測パネルの「速度比」「突進」2行と**突進中に枠が金色になる**のは残す（しきい値を詰めるための表示）。

被ダメージ軽減は他の伸びと同じく溜めに比例する。100 のダメージを入れて実測した値:

| 強化 | 最大軽減 | 突進なし | 溜め50% | 溜め100% |
|---|---|---|---|---|
| なし | 0% | 100 | 100 | 100 |
| カード1枚 | 15% | 100 | 92.5 | 85 |
| カード3枚＋ツリー | 60% | 100 | 70 | 40 |

負荷（実測・150体が全員突進中）: 丸い弧 **0.050 ms/frame**、尖った形 **0.035 ms/frame**、ヒットエフェクト 40個で **0.032 ms/frame**。

#### 残っている論点

- 直進していると 100% の時間で突進が続く。**設計どおりだが「常時ON」に近い**ので、
  99.5% を上げるか `exitSpeedFrac` の幅を広げるかは実機の手触り次第。
- ヒットストップは突進を切らない（上記）ので、「建物に当たって止まることが突進解除の契機になる」
  という設計をやるなら、**ヒットストップ中は速度ベクトルも落とす**か、
  `flockMetrics` 側で凍っている個体を速さ 0 として数えるかのどちらかが要る（未着手）。

### 2-1ad. ブレスの攻撃可能角度（v0.90）

Shooter 指示。「今は全員最初から360度。竜種の個性として初期の攻撃角度に差をつけ、
ラン中の強化で広げられるようにする。蛙竜など別枠の竜種は除外で良い」。

#### 仕組み

`SPECIES_DEFS[x].breathArcDeg` = **前方の合計角度（度）**。360 で全方位（従来通り）。
未記入の竜種は 360 扱い＝**別枠の竜種は自動的に除外**される。
判定は `isInBreathArc(i, tx, ty, halfArc)` で、向きは**速度ベクトル**（＝竜のスプライトが向いている方向）。
ほぼ止まっている個体は向きが定まらないので制限しない。

| 竜種 | 初期角度 | 理由 |
|---|---|---|
| 火竜 | **30°** | 「目の前を焚く」種。群れを向けないと当たらない |
| 氷竜 | 70° | 射程は長いが槍を置く種なので少しだけ広い |
| 影竜 | 150° | 弾が追尾する＝向きを合わせる必要が薄い |
| 燕竜・彗星竜 | 90° | 散弾は元々前へ広がるので中間 |
| 緋竜・隼竜・蜂竜・ガーゴイル・爆竜・惑竜・蛙竜・UFO | 全方位（除外） | 下記 |

除外の理由: 緋竜は体当たりのみ、隼竜の刃翼は元々前方扇、蜂竜の衛星は照準しない、
ガーゴイル・爆竜・惑竜は真下へ落とす、蛙竜の舌は元々真っすぐだけ。
**UFO は進行方向を向かない**（`noTail` + `spin` で自転する）ので、向きに依存する制限をかけても
画面から読めない＝ここが一番はっきりした「別枠」。

適用先は照準する4種類の攻撃（`beam` / `bullet` / `missile` / `scatter`）。
`findNearestBuilding` に `boidIdx` / `halfArc` の省略可能な引数を足した
（省略時は従来通り全方位。飛行中の弾の再ロックなどはそのまま）。

強化はラン中カード「見渡す顎」1枚 +40°、最大4枚。
**既に全方位の竜種ではプールに乗せない**（`needsBreathArc` で空振りカードを作らない）。

**v0.90.1: 一番最初のランだけは無条件で全方位**（`currentRunIsFirst` で分岐。Shooter指示）。
初回は竜種を選ばず火竜で即開始する導入のランなので、ここで「向けないと当たらない」を
教えると手順が多すぎる。角度を最初から強化済みの状態で渡し、竜種の個性としては2回目以降に登場させる。

実測: 初回ランは定義値 30° に対して実効 360°、強化カードも出ない。
2回目のランに入ると実効 30° に戻り、カードもプールに出る。
中断再開のセーブにも `isFirstRun` が入っているので、初回ランを再開しても 360° のまま。

**落とし穴**: v0.90.0 ではこのカード名の漢字を U+9871 と書き間違えていた（正しくは U+984E）。
パッチを `\u` エスケープで書くとこの種の誤字は目で見つからない。v0.90.2 で修正。

#### 実測

**① 角度そのものは正確に効く。** 火竜（30°＝±15°）で、竜1体の向きを建物の方向から
ずらしながら 1.5 秒ずつ焼かせた結果:

| 向きのズレ | 0° | 10° | 14° | 16° | 20° | 45° | 90° | 180° |
|---|---|---|---|---|---|---|---|---|
| dps | 1.4 | 1.7 | 1.1 | 0.3 | 0.1 | 0 | 0 | 0 |

±15° の境界でぴたりと落ちる（16°・20° に僅かに残るのは、計測の 16ms 間隔の間に
シムが竜を動かして向きがずれるぶん）。

**② カードで広がる。** 火竜 30 → 70 → 110 → 150 → 190°。4枚でプールから消える。
緋竜・蛙竜・蜂竜ではカードが出ないことも確認した。

**③ ただし街の中では攻略速度がほとんど変わらない。**
8秒間、街の上に居座らせて破壊数を測った（街ごとの差を打ち消すため割り当てを入れ替えて2組）:

| | 30° | 360° |
|---|---|---|
| 1組目 | 59/94 棟 | 76/92 棟 |
| 2組目（街を入れ替え） | 74/85 棟 | 69/99 棟 |

**向きが逆転する＝街ごとのばらつきに埋もれている。** 4体まで減らしても与ダメージは
450 対 450 でまったく同じだった。理由は明快で、**密集した街では常に前方15°の中に何かある**ため、
制限が発動する場面がほとんど無い。

**④ 孤立した標的では効く。** 街から離れた1棟だけを的にして8体で焼くと:

| 角度 | 30° | 70° | 150° | 360° |
|---|---|---|---|---|
| dps | 18.1 | 22.2 | 13.0 | 30.5 |

360° の 30.5 に対し、制限ありは 13〜22。おおむね半分前後まで落ちる
（150° が一番低いのは周回位相の運。この測定はばらつきが大きい）。

#### 分かったこと

**竜種の手触り（前を向いて焚く）としては機能するが、街攻略のバランス調整の軸にはまだなっていない。**
バランス側の軸として使いたいなら、街の中でも効くように次のどれかが要る（いずれも未着手）。

- 角度をもっと狭くする（15°など）。ただし火竜が扱いにくくなりすぎる恐れ
- 体当たり（直接攻撃）にも同じ角度制限をかける
- 「角度外は威力半減」のような連続的な減衰にして、密集地でも差が出るようにする

#### 見せ方

**専用の表示は付けていない。** ブレスが前方へ出ることそのものが表示になっている
（後ろの建物が燃えないことで伝わる）。調整用に計測パネルへ「ブレス角」の行を足した。
初見で角度が読めないようなら、扇の薄い目印を足すか検討する。

### 2-1ae. 図鑑に「特殊個体」タブ（v0.92）

Shooter 指示。敵・建物・弾に続く4つ目のタブ。

特殊個体は**専用の絵を持たない**（普通の竜＋エフェクトなので）。
そこで弾のページと同じく **canvas を後入れして特徴的な形を描く**（`codexSpecialCanvas`）。

| 竜 | 描いている形 |
|---|---|
| 灯竜 | 中心から伸びる金の光条（先ほど細く薄くなるグラデーション） |
| 巌竜 | 他の2種より明らかに大きい丸＋砕けた破片 |
| 呑竜 | 吸引の破線の輪＋周回する溜め弾 |

数値は定数から直接引いている（`BEACON_LENGTH` / `HEAVY_RAM_DAMAGE` / `DEFLECT_RADIUS` など）ので、
バランスを触れば図鑑も自動で追従する。

末尾に「覚えておくこと」として2件だけ補足を置いた。
**巌竜は遠隔攻撃を持たない**ことと、**呑竜は弾幕を消せない**こと（実測17%）。
どちらも遊んでいて誤解しやすく、誤解したままだと選択を誤る類なので明示する。

#### ついでに直した表示の不具合

図鑑の本文に `**強調**` と書いてある箇所が、HTML なので**アスタリスクがそのまま出ていた**。
v0.68 の建物ページから残っていたもの。`<b>` に置き換えて4箇所直した（3箇所は既存、1箇所は今回追加分）。

### 2-1af. 呑竜の吸引を群れサイズに／母竜を虹竜として特殊個体へ（v0.93）

#### ① 呑竜が全然吸えていなかった

Shooter 判定。「吸う範囲をもっと大きく。すごくインターバルがあるので基本群れを覆う大きさでいい」。

半径を 70 → 200px（群れの広がりは実測 σ64〜114px・最遠個体まで 106〜263px）にしたが、
**それだけでは 15% → 24% にしか上がらなかった**。内訳を測ると理由が出た。

| 設定 | 吸収率 | 吸える時間 | 満杯待ち | クールダウン |
|---|---|---|---|---|
| 半径70・容量10 | 15% | 70% | 10% | 20% |
| 半径200・容量10 | **24%** | 40% | 20% | 40% |
| 半径200・容量30 | **48%** | 70% | 10% | 20% |

**律速は半径ではなく「容量 × 周期」だった。** 広げるとすぐ満杯になり、
満杯待ち 1.5 秒＋クールダウン 3 秒のあいだ吸えないので、広げたぶんが捨てられていた。

採用は 半径 200 / 容量 24。実測 **37%**（吸えた29発・被弾49発）。
強化カード「大食らい」も +4 → +8 に上げた（基礎24に対して +4 では効いた気がしないため）。

溜め弾の描画も直した。24発を半径16pxの輪に並べると団子になるので、
**溜まるほど輪を広げて粒を小さくする**（`orbit = 16 + 16 × 溜め率`）。

#### ② 母竜を「虹竜」として特殊個体の1体に

Shooter 指示。名称も 母竜 → **虹竜**。

| | v0.92 まで | v0.93 |
|---|---|---|
| 居場所 | スロット0固定・**常に居る** | ★カード「虹竜」で加入。特殊個体の枠を1つ使う |
| 体格の成長 | レベルで常に育つ | 虹竜が居るランだけ |
| ブレス | ★「母なる吐息」で解禁 | 加入そのものが発動条件（解禁カードは廃止） |
| HP | ツリーの motherHp だけ | 基礎 ×2.5 ＋ ツリーの motherHp |

実装は呼び出し側を書き換えずに済むよう、古い名前の関数の中身だけ差し替えた。

- `isMotherDragon(i)` → `boidSpecial[i] === SPECIAL_RAINBOW`
- `isMotherActive()` → `rainbowSlot() >= 0`
- `rainbowSlot()` を新設（生きている虹竜のスロット番号、居なければ -1）
- `updateMotherBreath` は `MOTHER_DRAGON_IDX` ではなく `rainbowSlot()` の位置から撃つ
- `MOTHER_DRAGON_IDX` は削除（スロット固定をやめたため）
- カード: `mbreath_unlock` を廃止し `sp_rainbow`（specialJoin・max 1）へ。
  `mbreath_dmg` / `mbreath_rate` は `specialOf: SPECIAL_RAINBOW` に変更
- ツリーの分類名と2ノード名を虹竜表記へ（効果と id は据え置き）

実測: 加入前はスロット0の体格 1.00・ブレス発動なし。加入すると体格 1.42（Lv7）・
HP 75（通常30）・7秒ごとに6体を薙ぐ（16秒で12回・482ダメージ・8棟破壊）。
カードプールも 0体→加入4枚、虹竜のみ→虹竜の強化2枚＋他の加入3枚、枠満杯→強化のみ、と正しく切り替わる。

#### 常時成長を戻さないこと（確定）

v0.92 まではスロット0がブレスの有無に関わらず常に育っていたので、
この変更で「レベルアップが群れの見た目に出る手掛かり」が減るとして確認を取った。

**Shooter 判定（2026-09-20）: 「特殊個体がいるわけでもないのに
『レベルが上がると育つ竜が1匹いる』のはユーザーから見て意味不明なので、
なくて大丈夫」。**

つまりそれは失った見せ場ではなく、**説明のつかない異形だった**。
能力を持たない竜が1匹だけ大きい状態には戻さないこと。
（コード側にも `MOTHER_DRAGON` の見出しコメントとして同じことを書いてある。
v0.18 時代の「スロット0固定」の説明が残っていたので v0.93.1 で書き直した）

### 2-1ag. 動員を実際に強くする／街ごと復活／内容をテキストで見せる（v0.94）

Shooter 指示。「動員で敵が強くなった感じがあまりない。もっと強く。
街の復活は全体を満遍なくではなく、完全回復する街とそのままの街があっていい。
あと動員で何が起きたかテキストで表示して」。

#### ① 倍率を2度上げた（1度目は効かなかった）

最初 hp 1.35→1.80 / dmg 1.20→1.50 にして測ったが、**ほとんど何も変わらなかった**。

| | 1棟の平均HP | 12秒の破壊数 | 被ダメ/秒 |
|---|---|---|---|
| 平時 | 15.4 | 60 | 28 |
| 動員（hp×1.8） | 25.9 | **61** | **30** |

**群れ30体の火力に対して HP 26 は依然として一瞬で消える量**で、
建物が撃ち返す前に落ちるため被ダメージも増えなかった。そこでもう一段上げた。

採用値と、その結果（同じ規模の街・12秒・群れ30体・ダウンは即復帰させて比較）。

| 段階 | HP倍率 | 火力倍率 | 部隊倍率 | 1棟の平均HP | 12秒の破壊数 | 被ダメ/秒 | ダウン | 移動敵 |
|---|---|---|---|---|---|---|---|---|
| 平時 | 1.0 | 1.0 | 1.0 | 15.4 | 64 | 23 | 0 | 37 |
| 動員 | **2.6** | **1.9** | **2.0** | 38.7 | 59 | 39 | 2 | 61 |
| 総力戦 | **4.2** | **2.7** | **2.8** | 65.6 | 48 | 70 | 4 | 77 |
| 決戦 | **6.5** | **3.6** | **3.6** | 103.8 | 37 | 72 | 3 | 101 |

平時→動員で **被ダメージ +70%・初めてダウンが出る・移動敵 +65%**。
破壊速度は 64→59 とわずかに落ちるだけなので、進めなくなるのではなく「代償が増える」形。

旧値は hp 1.00/1.35/1.80/2.40、dmg 1.00/1.20/1.45/1.75、部隊 1.0/1.3/1.6/2.0。

#### ② 再建を街単位に

`rebuildRuinsForTier` の選び方を変えた。旧実装は**廃墟全体から 30% をランダムに拾う**ので、
壊した街がどこも中途半端に半分戻るという読みにくい絵になっていた。

- 廃墟を `_townIndex` でまとめ、街をシャッフルして**予算を使い切るまで丸ごと**建て直す
- 予算を少し超えてもその街は最後まで建てる（**半分だけ戻った街を作らないため**）
- 街に属さない廃墟（まばらな集落）は卵の供給源なので、従来どおり 30% を抽選

実測: 3つの街を全壊させてから動員すると、1つが 180/180 棟すべて復活し、
残り2つは 101/101・125/125 が壊れたまま。**「部分的」に戻った街は0**。

#### ③ 何が起きたかを出す

段階名しか出ていなかったので、副題に内訳を出す。

`街2つが完全復活(175棟) ／ HP×2.6 ／ 火力×1.9 ／ 部隊×2.0`

倍率は**前の段階からの比**（累積値ではない）。375px 幅で 2 行に収まることを実測で確認した
（最初は語を詰めずに書いて3行になったので短縮した）。

加えて、**復活した街の上に `再建 N棟` のワールドテキスト**を出す。
どこが戻ったのかは画面中央のバナーでは伝わらないため。

### 2-1ah. 特殊個体「機竜」（v0.95）

Shooter 指示。「初速0から加速していく大きなロケット弾を発射。発射頻度は虹竜と同じ。
着弾したら爆発範囲攻撃。誘導はなく前進。強化すると発射数が増える。
扇状に最大10発で、同時発射ではなく 0.3 秒くらい間を空けて撃っていく」。

#### 中身

| 項目 | 値 | 定数 |
|---|---|---|
| 発射間隔 | 7秒（虹竜と同じ） | `effMechaInterval` → `MOTHER_BREATH_INTERVAL` |
| 発射数 | 3発（強化で最大10） | `MECHA_SALVO_BASE` / `MECHA_SALVO_MAX` |
| 1発ごとの間隔 | 0.30秒 | `MECHA_SALVO_GAP` |
| 扇の幅 | ±36度 | `MECHA_FAN` |
| 速度 | 初速0 → 最高 520px/s（加速 300） | `MECHA_ACCEL` / `MECHA_MAX_SPEED` |
| 爆発 | 威力70・半径72px | `MECHA_DAMAGE` / `MECHA_BLAST_R` |
| 寿命 | 3.2秒（何にも当たらなければ自爆） | `MECHA_LIFE` |

**扇は端から端へ順になぞる。** `k / (total - 1)` で割り付けるので、
撃っている途中に群れが向きを変えるとその分だけ散らばる。
向きは発射のたびに現在の進行方向を読む（斉射開始時に固定はしない）＝常に前へ出る。

弾は速度ベクトルではなく **「向き＋速さ」** で持つ（直進しかしないため）。
プールは `mrocket*`（80発）。`updateSpecials` の末尾で更新するので、
**機竜が落ちても飛んでいるロケットは進み続ける**。

一連射の途中はどの発目かを知る必要があるので `boidSpecialTotal` を足した
（`boidSpecialStock` が残り発数、`boidSpecialTimer` が次の1発までの間隔、
`boidSpecialCd` が次の斉射までの間隔）。ダウンすると一連射は打ち切られる。

#### 実測

発射のタイミング（20秒・群れ20体・開けた場所で直進）:

```
斉射       t=0.00 / 7.10 / 14.88      → 7秒間隔（虹竜と同じ）
斉射の中   0.30 / 0.31 / 0.30 秒間隔   → 設定 0.30 どおり
```

強化を最大まで積むと 1 斉射 10 発、扇は -37.4度 から +33.5度 まで **70.9度**
（設定 71.0度）を端から端へ。

加速カーブ（1発目を追った値）:

| 経過 | 0 | 0.23 | 0.44 | 0.66 | 0.88 | 1.10 |
|---|---|---|---|---|---|---|
| 速さ px/s | **0** | 68 | 132 | 197 | 264 | 329 |
| 進んだ距離 px | 0 | 8 | 30 | 67 | 119 | 183 |

最高速に届くのは約1.7秒（520 ÷ 300）。**最初の0.2秒で8pxしか進まない**ので、
竜の目の前に滞留してから後で伸びていく。この「遅れて届く」間が他の特殊個体と一番違う。

爆発は 70 の単発だが範囲なので、街の密集地で1発撃つと **242 ダメージ・2棟破壊** になった。

#### 落とし穴（また踏んだ）

パッチを `\u` エスケープで書いたせいで漢字を2度間違えた。

- `\u64b1`（撱）を `\u6483`（撃）のつもりで書いていた → 図鑑に「撱った向きに」と出ていた
- カード名を「多誘装填」にしていたが、機竜のロケットは**無誘導**なので「多連装填」に直した

**対策として、追加した日本語を実機で全部読み返す手順を今回も通した**
（`STRINGS.cards` と `CODEX_SPECIAL_*` を eval で出力して目視）。
v0.90 の「顎」、v0.92 の「踏」に続いて3度目なので、日本語を足すパッチでは必ずこの確認をする。

### 2-1ai. 動く敵8種の向きと図鑑の表記（v0.96）

Shooter 指示。「タイトルの『敵図鑑』を『図鑑』に」「動く敵で画像の向きが前後逆なものを直して」。

#### 直した8種

`ENEMY_SPRITE_META` の `forward` を `"up"` → `"down"` にした（**画像は触っていない**）。
`drawMovers` は `forward:"up"` なら `rotate(angle + π/2)`、`"down"` なら `rotate(angle - π/2)` なので、
これだけで進行方向に対して180度回る。`px/py` はアルファ重心なので支点はそのままでよい。

knights / clubmen / mammoth_lord / bullchariot / gilded_colossus / batteringram / shockman / teslagiant

変更後、`forward` の内訳は down 8・up 19・none 11（計38）。**指定された8種とちょうど一致**。

#### なぜ逆に見えていたのか（根本の原因）

元画像を並べて確認したところ、**この8種だけ「正面から見た立ち絵」で、他は真俯瞰の絵**だった。

| | 絵の作り |
|---|---|
| 正しく見えていた敵（raider / warlord / ironclad / teslawagon ほか） | 真上から見た図。前が画像の上 |
| 今回の8種 | 正面を向いた立ち絵。顔がこちらを向いている |

立ち絵は「前」が画面の手前を向いているので、真俯瞰の規約（画像の上＝前）が当てはまらない。
判定の決め手はマンモスで、**牙が画像の下側にあるため `"down"` にして初めて牙が進行方向を向いた**。
牡牛戦車の角と破城槌の衝角も同じく画像の下側にある。

**つまりこれは向きの設定ミスというより、[[dragon-tide-is-top-down]] に反する絵が8枚混じっていた**という話。
**v0.97 で絵から描き直した（下記）ので、`forward` は全部 `"up"` に戻してある。**

### 2-1aj. 8種を真俯瞰で描き直す（v0.97）

Shooter 指示「今のうちに絵から直しておきますか」。v0.96 の暫定対応を本筋に置き換えた。

#### 生成プロンプトの穴

`tools/gen_enemy_sprite.sh` には元から `Top-down view seen from directly above` と書いてあった。
**それでも正面の立ち絵が返ってくる。** 建物スプライト（§2-1t）で踏んだのと同じ穴。
「俯瞰で」と言うだけでは足りず、**見えてはいけないものを名指しする**必要がある。

```
STRICT OVERHEAD MAP VIEW. The camera is a bird directly above, looking straight DOWN.
You see ONLY the TOP surfaces: the top of the head, the shoulders, the back, the roof.
You must NOT see the face, the eyes, the chest, the belly, or any front-facing surface.
No perspective, no side faces, nothing seen in elevation.
This is NOT a character portrait and NOT a front view.
```

この文言で1体試したところ一発で真俯瞰（馬の頭とたてがみを上から見た騎士）になった。

#### 前後の指定も明示が要る

8体中2体（破城槌・衝撃兵）は俯瞰にはなったが**前後が逆**（衝角と頭が画像の下）だった。
`The forward direction points toward the TOP` だけでは足りず、
**その敵の一番前にある部位を名指しして「それを画像の上に置け」**と書いたら直った。

```
The iron ram head must be at the TOP of the image and the rear of the cart at the BOTTOM.
Its low horned head is at the very TOP of the image, the spined tail is at the BOTTOM.
```

#### 手順

1. `tools/gen_sprite_batch.sh` で生成（`name|aspect|forward|desc` の4体ずつ）
2. 生成直後は 440〜960px と大きいので、**長辺320px以下へ PIL で縮小**（旧絵も 160〜320px だった）
3. 縮小後のアルファ重心で px/py を取り直し、drawScale も再計算
4. `ENEMY_SPRITE_META` を書き換え、`forward` を全部 `"up"` へ
5. 実機で 8体を横一列に並べて全部右へ進ませ、絵の前が右を向くことを目で確認

`gilded_colossus` の `hover: true` はバッチ出力に含まれないので手で戻した。

#### 落とし穴

メタを正規表現の**後方参照**（`\1`）で置き換えたら、キー名が消えて
`ironclad: {...},{...}` のように**違う行に連結**された（構文エラーで検知）。
行単位の素直な置換に切り替えて解決。**メタの一括書き換えに後方参照を使わないこと。**

#### 追記（v0.97.1）

黄金の巨像だけ俯瞰にはなったが前後が逆のままだった（Shooter 指摘）。
描画側を触らず、**PNG 自体を 180 度回してアルファ重心を取り直す**方が安い
（`px/py` は 0.498/0.480 → 0.499/0.515）。
再生成すると絵柄が変わってしまうので、**向きだけの問題なら画像を回す**。

### 2-1ak. 特殊個体に専用の絵を与える（v0.98）

Shooter 指示「特殊個体の竜たちも専用画像を持つようにしたい」。

#### 何をしたか

**群れの竜種の絵を上書きする**方式にした。火竜のランでも氷竜のランでも、
灯竜は常に灯竜の姿で出る。足元リングだけでは群れの中で見失うのが理由。

| 特殊個体 | 絵の要点（小さく描いても読める特徴） |
|---|---|
| 灯竜 | 背中に**光る灯火の結晶**を載せた金の竜 |
| 巌竜 | 岩板に覆われた**丸く分厚い**シルエット。頭も脚も短い |
| 呑竜 | 頭の大半が**巨大な口**。真上から喉の奥まで見える |
| 虹竜 | 玉虫色の鱗と**結晶の冠**。細身で気高い |
| 機竜 | 鉄板とリベット。背中に**ロケットの筒**が2本 |

竜種と同じカテゴリA（body + wing×1）なので**描画経路は完全に共通**。
`DRAGON_PART_SPRITES` に5件足し、`getSpecialSprites(kind)` を新設して
`drawBoids` のスプライト選択を差し替えただけで済んでいる。
`SPECIAL_DEFS[].key` がそのまま `DRAGON_PART_SPRITES` のキーになっている。

#### 一緒に直したところ

- **尻尾の色**: 胴体だけ差し替えると尻尾が群れの竜種の色のまま残り、
  胴と尾が別の生き物に見える。`DRAGON_ELEMENT_COLORS` に5色足して個体ごとに引く。
- **円盤（UFO）の群れ**: 円盤は尻尾を持たず自転するが、**特殊個体は普通の竜なので
  尻尾を引き進行方向を向く**。`speciesNoTail` の判定に「特殊個体は除く」を足した。
- **スプライトキャッシュ 3 → 8**: 同時に要る列が「群れの竜種＋跳躍ポーズ＋特殊個体3体」で
  最大5列になる。3 のままだと LRU が毎回落ちて**毎フレーム16コマ焼き直す**。
  実測で 6秒間の再生成 0 回・62fps を確認した。
- **図鑑**: 中心の丸を実物のスプライトに差し替え（鼻先を上に向けて一覧で向きを揃える）。
  能力を表す形（光条・吸引の輪・ロケットの扇）はそのまま周りに残す。

#### 生成の実務

`tools/gen_dragon_sprite.sh <species> "<体>" "<翼>"` がそのまま使えた。
竜の型（真俯瞰・鼻先を上・尻尾なし・片翼のみ）は既に通っている型なので**5種とも1発**。
v0.97 の敵スプライトと違い「前後が逆」も出ていない。

### 2-1al. 弾を画像にする（v0.98.1〜0.98.2 ／ まず投槍と弩の2種だけ）

Shooter 判定「投槍と弩の見た目もチープなので改善したい」。
8種まとめてやる前に**2種だけ作って実寸で見比べる**という段取りにした。

#### 先に潰した懸念

| 懸念 | 実際 |
|---|---|
| 性能（最大900発） | **むしろ得**。今は1発ごとに線とパスを数本引いている。`drawImage` 1回のほうが軽い |
| 色が死ぬ | **本当**。`projectileColor` は建物の規模ごとに違う（小 `#c0a060` 〜 ボス `#ff6020`）。→ `source-atop` で薄く色を乗せた複製をキャッシュして解決（`shotTinted`） |
| 小さすぎて効果が出ない | **絵の作り方次第だった**。下記 |

#### 一番効いたこと: 絵を「細いまま潰れさせる」

最初、実物どおりの比率（全長が太さの11.7倍）で出てきた投槍を見て、
実寸25pxで高さ2.2pxにしかならないことを問題だと判断し、
**「全長は太さの5倍程度」と指示して短太い絵を作り直した**。これは**間違いだった**。

Shooter 判定（2026-09-20）:

> 矢弾を大きくしないでください。小さすぎて効果が出ないなんてことはないです。
> 矢がチープに見えたのは、綺麗に整いすぎた単純図形だからです。
> 画像が小さくて潰れていても全く問題ありません。
> むしろ綺麗な絵が乱れ飛んでいる現状の方がチープに見えます。

**チープさの原因は解像度ではなく「整いすぎ」だった。**
ベクター版は左右対称の直線と三角形しか無く、どの弾も完全に同じ形をしている。
そこが玩具っぽさの正体で、細部が見えるかどうかは関係ない。

したがって採用は**実物比率のまま（投槍 11.6:1 / 弩 6.0:1）**。
実寸では高さ2.2pxまで潰れて、木肌と穂先の色の差だけが残る**にじんだ筋**になる。
それでいい。読ませたいのは「向きと速さ」だけで、形の細部ではない。

**この教訓は弾に限らない。** 小さく描くものを「読めるように」整えると、
整えた結果そのものがチープに見える。潰れることを前提に描かせる。


#### 寸法の合わせ方

`SHOT_IMAGE_GEO` に `front`（原点→穂先）と `back`（原点→矢尻）をベクター版と
**同じ数値**で持たせ、画像をその長さに合わせて描く。高さは画像の縦横比に任せる
（引き伸ばして太らせない）。こうすると当たり判定も進行感も変わらず見た目だけ差し替わる。

| | front | back | 全長（通常 / カタパルト） |
|---|---|---|---|
| 投槍 | 7 | 15 | 25.3px / 39.2px |
| 弩 | 4 | 12 | 16.0px / 24.8px |

残り6種（投石・鉛玉・榴弾・放電弾・曳光弾・プラズマ）は**未着手**。
この2種の実機判定を待ってから決める。

#### 視認性の立て直し（v0.98.3）

Shooter 判定「見た目は良くなったが、さすがに視認性が悪すぎる。
他の時代の弾丸は現状で十分いい」。**残り6種はやらない**ことが確定。

原因を輝度で測った（地面に合成した実効値。0〜255）。

| | 平均輝度 |
|---|---|
| 地面 | 53 |
| 旧ベクター `#c0a060` べた塗り | **162** |
| 投槍の画像（v0.98.2・ティント0.30） | 84 |
| 弩の画像（同上） | **69** |

**弩は地面とほぼ同じ輝度で、見えないのが当然だった。** 面積はベクター約70px²に対して
画像56px²でほぼ同じなので、欠けていたのは大きさではなく**値**。
原因は2つ重なっている。元絵自体が暗い（原寸の平均輝度 投槍92・弩58）ことと、
**2〜3pxまで縮むと太い黒縁と半透明の縁が地面と混ざって全体が沈む**こと。

対策の第1手として**ティントだけ**を振った（`SHOT_TINT_ALPHA` 0.30 → 0.70）。
加えて、乗せる色をそのまま使わず **0.35 だけ白へ寄せてから**使う（`SHOT_TINT_LIGHTEN`）。
ボスの `#ff6020` は彩度は高いが輝度125しかなく、そのまま乗せると**逆に暗くなる**ため。

| ティント | 投槍 小集落 | 投槍 ボス | 弩 小集落 |
|---|---|---|---|
| 0.30・白寄せ無し（旧） | 84 | 78 | 69 |
| 0.70・白寄せ0.35（採用） | **108** | **99** | **96** |

ティントだけで到達できる上限は平均108あたり（ベクターの162には届かない）。
縁の半透明部分が地面と混ざるぶんは、色を乗せても取り返せないため。
足りなければ次は**黒縁を持たない絵に描き直す**（原寸の平均輝度が上がる）、
それでも足りなければ**弩の元絵を明るい配色で描き直す**。

#### 個体差と首振り（v0.98.4）

絵と明るさが決まったあと、Shooter 指示で B-1（弾ごとの個体差）と B-4（飛行中の揺れ）を追加。
**絵を差し替えただけでは「判を押したような並び」は消えない**（全弾が同じ画像なので）。

- **個体差**: 全長 ±10%、進行方向からの傾き ±0.12rad（±7度）
- **首振り**: 振幅は投槍 ±5.7度・弩 ±2.6度。
  速さは **rad/s ではなく周期（秒）で持つ**（v0.98.5）

いずれも**見た目だけ**で、当たり判定にも速度にも触っていない。

**乱数は使えない。** `drawEraShot` は毎フレーム呼ばれるので `random()` を引くと
弾の形が毎フレーム暴れる。弾スロット番号のハッシュ（`shotVariant`）から決定的に作る。
スロットは使い回されるので厳密には「弾ごと」ではなく「スロットごと」だが、
900枠あるので同時に飛んでいる弾が同じ変形になることはまず無い。
900スロット分の分布を実測して、全長・傾きとも偏りが無いことを確認済み
（8分割のヒストグラムで各ビン86〜145、傾きの平均 +0.2度）。

傾きと首振りは足し算なので、**最大で ±12.7度**（投槍）まで振れる。
振りすぎなら `SHOT_TILT_JITTER` と `SHOT_WOBBLE` のどちらでも単独で下げられる。

#### 首振りの速さは飛行時間から決める（v0.98.5）

Shooter 判定「首振り頻度が多すぎて変に見える。発射から消滅までに2周するくらい」。

飛行時間を実測した（建物の攻撃半径を横切るのにかかる時間。弾はほぼこの距離で当たるか消える）。

| | 弾速 | 攻撃半径 | 横切る時間 |
|---|---|---|---|
| 投槍（古代） | 70〜85px/s | 180〜220px | **2.1〜2.9秒** |
| 弩（中世） | 105〜126px/s | 200〜260px | **1.9〜2.1秒** |

旧値は投槍2.7周・弩4.1周で、**特に弩が振りすぎ**だった（弾が速いぶん寿命が短いのに、
振りは速くしていたため）。周期を投槍1.30秒・弩1.00秒にして 1.6〜2.3周に収めた。

`SHOT_WOBBLE` は rad/s ではなく**周期（秒）**で持つ形に変えた。
「一生で何周するか」が意図なので、飛行時間と直接見比べられる単位でないと調整できない。

#### 「一生」は最大射程まで飛んだときのこと（v0.98.6）

Shooter 判定「矢弾の一生というのは最大射程まで飛んだときのこと。
**いつ当たるかわからないのだからそこはコントロールできません**」。

v0.98.5 は「攻撃半径を横切る時間」を一生とみなして秒で周期を決めていた。
これは基準の取り方が誤り。当たるまでの距離はプレイヤーの位置次第で毎回違うので、
秒で決めると**弾速の違いがそのまま振りの多さに出てしまう**。

そこで**時間ではなく「飛んだ距離」で振る**形に変えた。
位相を `進んだ距離 / 最大射程`（0〜1）にすると、弾速も射程も時代も無関係に
**最大射程まで飛んでちょうど `SHOT_WOBBLE_TURNS` 周**になる。
途中で当たった弾はその分だけ少なく振る。

| | 最大射程まで | 攻撃半径で当たると | その7割で当たると |
|---|---|---|---|
| 投槍 小 | 2.94秒 | 1.44周 | 1.01周 |
| 投槍 大（カタパルト） | 5.60秒 | 1.05周 | 0.73周 |
| 弩 中 | 2.16秒 | 1.84周 | 1.29周 |
| 弩 大（カタパルト） | 3.33秒 | 1.24周 | 0.87周 |

調整は `SHOT_WOBBLE_TURNS` ひとつ。振幅は別で `SHOT_WOBBLE[].amp`。

最大射程を出す式は `projMaxRange(i)` に切り出して**更新と描画の両方から引く**。
描画側は「消滅までのどこにいるか」を出すのだから、
実際に消滅を判定している式と同じものを見ていないと意味がない。

### 2-1am. 首振りは半周・処理コストの実測（v0.98.7）

#### 「1周」の定義を揃えた

Shooter 質問「一周って左右に揺れた後中央に戻るまでで一周ですかね？
それだと揺れすぎなんで、もしそうなら半周でいい」。**そのとおり**。

位相は `sin` に入れているので、**1周＝sin の1周期**。
中央 → 片側 → 中央 → 反対側 → 中央、と**左右両方に振って戻る**までを指す。
`SHOT_WOBBLE_TURNS = 0.5` にすると sin の半周期（π）しか進まないので、
一生の間に**片側へ弧をひとつ描くだけ**になる。採用値は 0.5。

位相には `seed` を足しているので、どの弧を描くかは弾ごとに違う
（全弾が揃って同じ動きをするのを避けるため）。
半周だと弾によっては「ほぼ一定の傾きのまま飛ぶ」ものも出るが、
それは**個体ごとの飛び姿の違い**として読めるので問題にしない。

#### 処理コスト（実測）

Shooter 質問「処理が重いようなら一周3秒とかで決め撃ちでもいい」。**決め撃ちの必要なし**。

300発ぶんを1フレームとして測った値（60fpsの予算は16.7ms）。

| | ms/frame（300発） |
|---|---|
| B-1 個体差（sin×2 のハッシュ） | 0.032 |
| 飛距離の位相（sqrt ＋ `projMaxRange`） | **0.009** |
| 首振りの sin | 0.040 |
| **追加ぶん合計** | **0.081（予算の0.5%）** |
| 参考: 画像を300発 drawImage するだけ | 約5.3〜6.0 |

**決め撃ち（時間ベース）にしても速くならない。** 節約できるのは「飛距離の位相」の
0.009ms だけで、代わりに要る `breathTime` ベースの sin のほうがむしろ僅かに遅かった
（0.045 対 0.040）。1発あたり 0.27μs で、支配的なのは `drawImage` のほう。

### 2-1ao. 敵へのダメージを数字で出す（v0.99・試験）

Shooter 指示「敵へのダメージを数字で表示するテストをしてみたい。
そのままゲームに入れるかもしれないし、最終的にデバッグ表示としてのみ使うかもしれない。
まずはゲームに入れる想定で」。既定ONで実装し、デバッグメニューで消せるようにした。

#### 1ヒット1個は出せない

この game は群れ30〜150体が街を同時に齧るので、ブレスのような持続ダメージは
**毎フレーム・全個体ぶん**発生する。実測（群れ35・118棟の街）:

```
reportDamage の呼び出し   735回/秒
  うち画面外（捨てる）     485回/秒
  うち既存の数字へ合算     238回/秒
  うち新しい数字を作る      12回/秒
```

素直に1ヒット1個出すと**毎秒700個以上**湧くことになる。そこで2段で間引いている。

1. **画面外の敵には出さない**（呼び出しの66%がここで消える）
2. **相手ごとに短い窓で合算**する。同じ敵への追加ダメージは、
   その敵の数字が `DMG_NUM_MERGE` 秒より若ければそこへ足し込む

合算のキーは敵オブジェクトそのもの（`target._dmgSlot` にスロット番号を書く）。
建物と移動敵で同じ仕組みが使える。

#### 合算の窓は長めが要る

最初 `MERGE 0.30 / LIFE 0.80` で出したら、**画面が「1」で埋まった**。
ブレス1体ぶんの0.3秒は damage 1 にしかならないため。

| | 同時表示の平均 | 数字の中央値 | 「1以下」の割合 |
|---|---|---|---|
| MERGE 0.30 / LIFE 0.80 | **42個** | **1** | 54% |
| MERGE 0.90 / LIFE 1.25（採用） | **7.6個** | **8** | 38% |

窓を3倍にすると個数が1/6、数字の大きさが8倍になる。
**「小さい数字がたくさん」より「意味のある数字が少し」**のほうが読める。

#### 処理コスト

同じ場面で数字ONとOFFのfpsを測って **55.7〜57.8 対 53.3〜58.3**、差は出なかった。
プールは96個で、実測の同時表示は平均7.6・最大でも63だったので溢れていない
（溢れたときは一番古いものを捨てる）。

#### 拾っている攻撃

`damageBuilding` と `damageMover` の2つの共通ヘルパーに入れたので、
弾・ミサイル・光条・範囲爆発・呑竜の撃ち返し・刃翼などは自動で乗る。
共通ヘルパーを通らず直接 `hp -=` している4か所（ブレス・体当たり・虹竜のブレス・洪水）は
個別に呼び出しを足した。**竜の被ダメージは出さない**（指示は「敵への」ダメージ）。

#### まだ決めていないこと

- 数字の意味が「1ヒット」ではなく「0.9秒ぶんの合計」になっている。
  1ヒットを見せたいなら合算をやめる必要があるが、そうすると上の個数問題に戻る
- 大きい一撃（40以上）だけ色と大きさを変えているが、閾値は当てずっぽう
- 本編に残すかデバッグ表示に落とすかは未決定（`debugShowDamageNumbers` の初期値だけの問題）

### 2-1aq. 突進の判定を個体ごとにできるか（v0.99.1 時点の調査・未実装）

Shooter 質問「今は群れ全体の速度で判定しているが、個別の竜ごとに判定に変更すると
問題ありそうか？」。**方式に問題は無いが、判定に使う値を変えないと機能しない。**

#### 個体の速度は「ほぼ常に最高速」

竜は巡航速度で飛んでいるので、個体の速さはほとんどの時間 99.5% を超えている。
重心速度が落ちるのは**個体が遅いからではなく、向きがばらけてベクトル和が相殺するから**。
つまり今の判定が測っているのは速さではなく**整列度**。

実測（群れ28〜35体）:

| | 渦巻いている間 | まっすぐ飛ばした間 |
|---|---|---|
| 個体の速度が99.5%以上（提案の判定） | **18〜50%** | 82% |
| 個体が速く**かつ群れの向きに揃っている** | **5%** | 80% |
| 重心の速度比（現行の判定） | 51% | 92% |
| 現行の突進ON率 | **0%** | 10〜25% |

**個体の速度で判定すると、渦巻いて何もしていない時でも群れの2〜5割が突進状態になる。**
威力×3・射程+22・ノックバック・被ダメ軽減が半常時かかることになり、
突進という「条件を満たしたご褒美」が消える。

#### やるなら「速さ」ではなく「速さ＋群れの向きへの整列」

個体ごとに `dot(個体の進行方向, 重心の進行方向) >= 0.97`（±14度以内）を足すと、
渦巻き中 5% / 直進中 80% と**現行より鋭く分かれる**（現行は 0% / 10〜25%）。
これなら個体判定にする利点（後ろで押し戻された個体は乗らない、
群れの先頭だけが突っ込んで見える）を取りつつ、条件性を保てる。

#### 個体化で他に手を入れる必要があるもの

- `chargeHold` / `chargeLevel` を個体ごとの配列にする（コストは軽い）
- **突進に入った瞬間の合図**（`onChargeEnter` の画面フラッシュと振動）。
  個体ごとだと毎フレーム誰かが入るので、そのままでは出しっぱなしになる。
  「群れの何割が突進に入ったか」で1回だけ出すなどの作り直しが要る
- HUD とデバッグパネルの「突進」表示は1個の値を出しているので、

### 2-1ar. 突進は「入口は群れ・持続は個体」へ（v0.99.2）

Shooter 指示「単純に個別にするのはやめる。気になっているのは、突進中に一部の竜が
止まったら全部の突進が消えてしまうところ。発動処理は今のままで、
一旦突進に入った状態から解除される際は、自分の速さが残っていたら解除されないように」。

#### なぜこれが効くのか（分布が二山だから）

街に突っ込んだ瞬間の個体速度を測ると、**中間がほとんど無い**（群れ28体・3202サンプル）。

| 個体の速度比 | 割合 |
|---|---|
| 98.5%以上（まだ飛んでいる） | **72%** |
| 95〜98.5% | 1% |
| 90〜95% | 2% |
| 80〜90% | 3% |
| 80%未満（止まっている） | **23%** |

同じ瞬間の重心速度比は **32%**。つまり**まだ全速で飛んでいる7割が、
止まった2割のせいで突進を失っていた**。

解除だけを個体の速さで見ると、この二山をそのまま切り分けられる。
閾値（`exitSpeedFrac` = 0.985）を跨ぐ個体がほとんど居ないので、
**閾値付近のちらつきも起きない**。

#### 仕様

- **入口は群れのまま**。重心速度比が `enterSpeedFrac`（0.995）以上で突進に入り、
  そのとき生きている全個体が突進状態になる
- **群れの条件が切れたら、個体ごとに自分の速さで判定**。
  `exitSpeedFrac` 以上なら突進を続ける
- **再点火は群れ側だけ**。一度落ちた個体が自分だけ復帰することはない
- 溜め（`chargeHold`）も個体ごと。威力・射程・ノックバック・被ダメ軽減・エフェクトは
  すべて**その竜の溜め**で引く

#### 実測

街へ35体で突っ込ませた場合（重心速度比は22〜95%を行き来する）:

```
t=0.0〜3.3s   35体が突進を維持   ← 旧実装ならこの間ずっと0体
t=3.6s        13体
t=3.9s         1体
t=5.7s         0体
```

**開けた場所で放置しても暴走しない。** 入った後そのまま置くと群れが渦を巻き始め、
個体速度が落ちて 40体 → 0体 へ約5秒で自然に解除された。

#### 見た目

突進エフェクト（尾と衝波）は**乗っている竜にだけ**出る。
どの竜が突進しているかが見えないと、個体で持続する意味が伝わらないため。
HUD も `群れON 35/45体` のように**何体が乗っているか**を出すようにした。

#### 未調整

占有率が上がったぶん、威力×3・射程+22・ノックバック190・被ダメ軽減は
**まだ調整し直していない**。実機の手応えを見てから。

## 4. 恒久ルール・制約（必ず守る）

- **トップビュー厳守**：ドーム/立面など横視点の形は禁止（干し草をドームにして差し戻した実績あり）。
- **敗北要素なし**：竜はダウンしても必ず復帰。ノーダウン系のチャレンジもコンセプト違反として不採用。
- **モーダルでプレイを止めない**：カード選択はスローモーで非モーダル。
- **音は当面後回し**。
- 「被り」（スタジオ内・過去の種・市場の先行作）は設計・判定の制約にしない。
- 変更は毎回 `/deploy-dragon-tide` で検証→master 反映。URLは装飾なしのプレーンテキストで単独行に。
- 全ユーザー向け文字列は `STRINGS` 経由、数値は定数に集約（マジックナンバー禁止）。
- **移動パラメータを名前付きプリセットに畳まない**（`move:"standard"` のような enum を作らない）。
  分離した目的がバリエーションなので、竜種ごとに全項目を自由に組み合わせられる形を保つ。
- **ピボット値の正典はコード内の定数**（`DRAGON_PART_SPRITES`）。`data/` へ外出ししない
  （v0.35.1 で JSON を削除。読まれないデータは腐る）。

### 検証の既知の罠（時間を溶かした実績あり）

- **プレビューが `data:` スナップショット化して相対パスの画像を読めない**ことがある。
  この状態では全竜種がベクター描画に落ちて見える＝**コードのバグと誤認しやすい**。
  `location.href` が `data:` で始まっていないか必ず確認する。
- `preview_screenshot` はタイムアウトする。見た目はユーザーの実機に委ねる。
- プレビューでは canvas サイズ0（`viewH=0`）。入力テストは `viewW/viewH` を390/844にしてから、
  または `isDrawing`／`touchRing`／`pathPush` を直接立てて `simStep(dt)` を回す。
- **`beginRun(weapon)` は `gameState !== "title"` で即 return する**。竜種を切り替えて比較するときは
  `flockSpecies` を直接代入して `resetBoidsForStageStart(n)`。
- **`mv()` は `moveProfileOverride|flockSpecies` をキーにキャッシュする**。同じキーのまま
  プリセットを書き換えてパラメータを振ると全条件が1本目の値で走る（スイープを丸ごと誤測定した実績あり）。
- **旋回性能は「◯度旋回にかかる時間」で測らない**。リーダーの方位が群れの移動につれて変わるため。
  1フレームごとの実回転量を積んで角速度を出す。180度ちょうどは左右どちらに回るか決まらない特異点。
- **竜種を順に走らせて掃討速度を比べると、先の種が町を壊して後の種が不利になる**。
  建物の hp/fallen を毎回復元してから測る。
- 構文チェックは `<script>` 内JSを**BOMなしUTF-8**で抽出して `node --check`。
  ただし **`node --check` / `tools/check.mjs` は構文しか見ない**。`const` の TDZ
  （宣言前の定数を参照）はロード時に初めて落ちるので、**編集後は必ずページを開いて
  コンソールを確認する**（v0.41 で `BOSS_RADIUS` を宣言前に参照して真っ白になった）。
- `generateStageLayout(idx)` は**返り値**で建物配列を返す（グローバル `settlements` を更新しない）。
- **震えの計測は個体0だけ見ない**。群れ全員の1フレームあたり回転量を平均する
  （個体0がたまたま輪の内側にいると正常でも異常でも数字が振れる。実際に一度誤判定した）。
- **回り込み・周回の「向き」を個体ごとに決めると半数が逆回りして正面衝突する**（v0.37）。
  群れの角運動量で全員揃える。詳細は controls.md §12-2d。
- **即時方向転換の竜は、分離を"向き"に混ぜると必ず震える**。分離は外力チャネル（kick）へ回す。
- プレビュー（このリポジトリの `preview_start`）では **`computer` のスクリーンショットも
  タイムアウトする**（"Browser pane is not displayed"）。見た目はユーザーの実機に委ねる。
  ただし **canvas の `getImageData` によるピクセル計測は動く**（跳躍の描画倍率もこれで確認した）。
